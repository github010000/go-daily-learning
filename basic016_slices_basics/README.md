## 한 줄 요약
슬라이스는 "배열을 가리키는 포인터, 길이(len), 용량(cap)" 세 가지로 이루어진 헤더 구조체와 같습니다.

## 왜 필요한가
슬라이스는 Go에서 가장 자주 쓰이는 자료 구조이지만, 그 동작 원리를 모르면 **"왜 내 변수가 바뀌지 않았지?"** 또는 **"왜 안 바뀐 변수가 바뀌었지?"** 하는 충격을 자주 겪게 됩니다.

다른 언어(Python의 리스트, JavaScript의 배열)는 슬라이싱(slicing)이나 복사(copy)를 할 때 대개 새 메모리를 할당해서 독립적인 객체를 만들거나, 참조를 명확히 구분합니다. 하지만 Go의 슬라이스는 **원본 배열을 공유**합니다.

즉, Go는 성능(메모리 할당 비용 절감)을 위해 슬라이스가 원본 데이터를 가리키도록 설계했습니다. 이 설계가 초보자에게는 **"데이터가 예상치 못하게 변한다"**는 형태로 돌아옵니다. 이 장에서는 슬라이스가 내부적으로 어떻게 생겼는지, 그리고 그 때문에 어떤 함정에 빠질 수 있는지를 이해해야 합니다.

## 기본 사용
슬라이스를 만드는 방법은 크게 세 가지입니다.

1.  **리터럴**: `s := []int{1, 2, 3}` — 컴파일 타임에 크기가 정해집니다.
2.  **make 함수**: `s := make([]int, 3, 5)` — 길이 3, 용량 5로 빈 슬라이스를 만듭니다.
3.  **슬라이싱**: `sub := original[1:4]` — 기존 슬라이스에서 부분만 잘라냅니다.

여기서 `len`은 현재 몇 개의 요소를 들고 있는지, `cap`은 슬라이스가 현재 얼마만큼의 여유 공간(내부 배열)을 확보하고 있는지를 의미합니다.

**핵심:** `append`를 할 때 현재 `len`이 `cap`을 넘어서면, Go는 **새로운 배열을 할당**하고 데이터를 복사한 뒤 그 배열을 사용합니다. 이때 기존 슬라이스는 여전히 옛날 배열을 가리키고, 새로 할당된 배열은 `append`가 반환하는 새 슬라이스가 가리킵니다.

## 실전에서는 이렇게 쓴다

실전 코드에서는 슬라이스를 함수에 넘길 때 두 가지 전략을 주로 씁니다.

1.  **불변성 유지**: 함수 안에서 `append`를 쓰되, 그 결과를 **반환**받아 호출하는 쪽에서 변수를 덮어씁니다. (예: `items = append(items, newItem)`)
2.  **원본 수정**: 함수가 슬라이스 헤더 자체(포인터 위치)를 바꾸지 않고, 배열의 요소만 건드려야 할 때는 `src[i] = val` 형태로 접근합니다.

또한, `make([]int, 0, 1000)`처럼 `cap`을 미리 충분히 잡아주면, 반복문 안에서 `append`할 때마다 배열이 계속 새로 할당되는 성능 병목을 피할 수 있습니다.

## 흔한 실수

### 1. 함수에서 append 후 원본이 안 바뀌었다고 놀라기
**틀린 코드**
```go
func add(s []int) {
    s = append(s, 1) // s가 새 배열을 가리킬 수 있음
}
func main() {
    nums := []int{10}
    add(nums)
    fmt.Println(nums) // [10] ... 왜?!
}
```
**일어났던 일:** 함수 내부에서 `append`로 인해 `cap`이 부족해 새 배열이 할당되었습니다. `s` 변수는 새 배열을 가리키게 되었지만, `main`의 `nums` 변수는 여전히 옛날 배열을 가리킵니다.
**왜 그런지:** 슬라이스는 값(type)으로 전달되기 때문입니다. 함수 파라미터는 원본의 복사본입니다.
**고친 코드:**
```go
func add(s []int) []int {
    return append(s, 1)
}
func main() {
    nums := []int{10}
    nums = add(nums) // 반환값을 받아야 함
    fmt.Println(nums) // [10 1]
}
```

### 2. 슬라이싱으로 만든 부분 슬라이스가 원본을 망가뜨리기
**틀린 코드**
```go
func main() {
    original := []int{1, 2, 3, 4, 5}
    sub := original[1:4] // 2, 3, 4
    sub[0] = 99
    fmt.Println(original) // [1 99 3 4 5] ... 원본이 변했다!
}
```
**일어났던 일:** `sub`의 요소를 수정했는데 `original`의 중간 값도 바뀌었습니다.
**왜 그런지:** 슬라이스는 독립된 데이터가 아니라 **원본 배열의 뷰(view)**이기 때문입니다. `sub`와 `original`은 같은 underlying array를 공유합니다.
**고친 코드 (복사가 필요하다면):**
```go
func main() {
    original := []int{1, 2, 3, 4, 5}
    sub := original[1:4]
    
    // 원본과 독립된 복사본이 필요하다면 copy 함수를 쓰세요
    subCopy := make([]int, len(sub))
    copy(subCopy, sub)
    subCopy[0] = 99
    
    fmt.Println(original) // [1 2 3 4 5] (변함 없음)
}
```

### 3. nil 슬라이스와 빈 슬라이스를 헷갈리기
**틀린 코드**
```go
var s1 []int       // nil 슬라이스
s2 := []int{}      // 빈 슬라이스

fmt.Println(json.Marshal(s1)) // null
fmt.Println(json.Marshal(s2)) // []
```
**일어났던 일:** JSON 직렬화 결과의 차이가 예상과 달랐습니다.
**왜 그런지:** `nil`은 "아무것도 없음"을, `[]int{}`는 "빈 것"을 의미합니다. `append(nilSlice, 1)`과 `append(emptySlice, 1)`의 실행 결과는 같지만(둘 다 `[1]`이 됨), 타입 시스템이나 직렬화 라이브러리에서는 이 둘을 구별합니다.
**고친 코드:** 보통 `var s []int`로 선언하는 습관이 더 Go스럽습니다(초기화 없이도 append 가능).

## 주의할 점

*   **슬라이스 vs 포인터**: 슬라이스를 넘길 때 요소는 공유되지만, 슬라이스 자체(헤더)는 공유되지 않습니다. 즉, `s[0] = 1`은 원본에 영향을 미치지만, `s = append(s, 1)`은 원본에 영향을 미치지 **않을 수** 있습니다.
*   **메모리 누수**: 긴 슬라이스에서 `sub := s[1:2]`처럼 아주 작은 부분만 잘라 쓰면, Go는 `sub`가 살아있는 동안 원본 배열 `s` 전체를 메모리에 계속 유지합니다. huge한 배열의 일부만 쓸 때는 주의해야 합니다.
*   **for range와 슬라이스**: `for i, v := range s`에서 `v`는 슬라이스 요소의 **복사본**입니다. `v`를 수정해도 원본 슬라이스는 바뀌지 않습니다.

## 코드로 확인하기

`go run .` 을 실행하면 다음과 같은 순서로 결과가 나옵니다.

1.  **슬라이스 전달 시 append 동작:**
    *   `원본 nums: [1 2 3]`
    *   `함수 호출 후 원본 nums: [1 2 3] (변함 없음)`
    *   `함수 반환값 result: [1 2 3 4]`
    *   **해석:** `sliceByVal` 안에서 `append`가 이루어졌을 때, 원본 배열의 `cap`이 부족해 새 배열이 할당되었습니다. 함수 파라미터 `src`는 새 배열을 가리키게 되었지만, `main`의 `nums`는 옛날 배열을 그대로 유지하고 있습니다. 이것이 Go의 슬라이스 값 전달 semantics입니다.

2.  **원본 배열 직접 수정:**
    *   `함수 호출 후 nums2: [10 99 30] (변경됨!)`
    *   **해석:** 슬라이스 헤더(포인터)는 바꾸지 않고, 가리키는 배열의 인덱스 `1`에 직접 `99`를 넣었습니다. 헤더는 같으므로 원본이 바뀝니다.

3.  **슬라이싱과 배열 공유:**
    *   `슬라이싱 후 original: [10 99 30 40 50] (의도치 않게 변함!)`
    *   **해석:** `sub`는 `original`의 중간 부분을 가리키는 뷰입니다. `sub[0]`을 건드리면 `original`의 두 번째 요소가 바로 바뀝니다.

4.  **nil vs 빈 슬라이스:**
    *   `nilSlice append 결과: [1 2]`
    *   `emptySlice append 결과: [1 2]`
    *   **해석:** 실행 결과값은 동일합니다. 하지만 코드 상에서 `var nilSlice []int`는 `nil`이고 `emptySlice := []int{}`는 빈 슬라이스입니다.

## 연습 문제

1.  **슬라이스 복사**: `append` 없이 `original` 슬라이스와 완전히 독립된(배열 공유 없는) 슬라이스 `copy`를 만드는 코드를 작성해 보세요. (`copy` 내장 함수를 사용하세요)
2.  **슬라이스 합치기**: 두 개의 슬라이스 `a`와 `b`를 받아, `a`의 용량(cap)을 넘어서지 않으면 `a`를 반환하고, 넘어서면 새 슬라이스를 만들어 `b`의 요소까지 합친 결과를 반환하는 `merge` 함수를 작성해 보세요.
3.  **메모리 절약**: 길이 1000인 슬라이스 `big`에서 마지막 3개의 요소만 담은 `tail`을 만들고 싶을 때, `big`의 나머지 997개 요소가 메모리에서 해제되도록(또는 GC 대상이 되도록) 주의하며 코드를 작성해 보세요. (힌트: `tail`이 `big`의 전체 배열을 잡지 않도록 자르는 위치를 신중히 선택해야 합니다)
