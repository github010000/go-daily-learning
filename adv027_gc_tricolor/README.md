## 한 줄 요약

뮤테이터가 도는 동안 마커가 힙을 훑으려면 "검은 객체는 흰 객체를 가리키지 않는다"와 "마킹 시작 시점의 간선이 지워지면 그 대상을 회색으로 만든다"를 동시에 지켜야 하고, Go 는 이 둘을 섞은 hybrid write barrier(삭제 + 조건부 삽입)로 마킹 종료 시의 스택 재스캔을 없애는 대신 포인터를 힙에 쓰는 모든 지점에 몇 나노초를 지불한다.

## 왜 이런 설계인가

가장 단순한 수집기는 세계를 멈추고 살아있는 객체를 전부 훑는다. 정확하고 배리어도 필요 없다. 문제는 정지 시간이 살아있는 힙 크기에 비례한다는 점이다. 힙이 10GB 이고 초당 수백 번 요청을 처리하는 서버라면, 마킹 한 번에 수백 밀리초를 멈춰야 하고 그때마다 p99 가 무너진다. "힙이 커져도 정지 시간은 그대로"라는 목표를 세우는 순간, 마킹을 뮤테이터와 동시에 돌리는 것 말고는 답이 없다. 그런데 동시에 돌리는 순간 그래프는 마커 발밑에서 변한다. 마킹의 정의 자체를 "움직이는 표적"에 맞춰 다시 써야 한다.

표적을 고정하는 방법은 두 가지다. 첫째는 마킹 시작 시점의 그래프를 기준으로 삼는 것이다(snapshot-at-beginning). 시작 시점에 살아있던 객체는 무조건 살린다. 둘째는 "검은 객체가 흰 객체를 가리키는 순간"을 금지하고 그 금지를 매 쓰기마다 강제하는 것이다(incremental update). 두 방법 모두 매 포인터 쓰기마다 런타임에 알려 주는 훅이 필요하고, 그것이 write barrier 다. 배리어가 없다면 마커가 이미 지나간 검은 객체에 흰색 참조가 새로 꽂히고, 그 흰 객체는 다시는 방문되지 않은 채 스윕에서 회수된다. 프로그램은 살아있는 포인터로 해제된 메모리를 읽는다.

Go 1.5 는 Dijkstra 삽입 배리어로 동시 마킹을 시작했다. 삽입 배리어는 새로 쓰는 값만 보면 되므로 이해하기 쉽다. 대신 치명적인 구멍이 있었다. Go 컴파일러는 스택 슬롯 쓰기에는 배리어를 넣지 않는다. 스택은 통째로 스캔되니까 넣을 이유가 없고, 넣으면 모든 함수 호출이 느려진다. 그래서 마커가 어떤 고루틴의 스택을 이미 훑고 지나간 뒤에 그 고루틴이 지역 변수로 포인터를 옮기고 힙에서 원본을 지우면, 마커는 그 객체를 영원히 못 본다. 이 구멍을 메우려고 Go 1.5부터 1.7까지는 마킹 종료 시 모든 고루틴의 스택을 세계를 멈추고 다시 훑었다. 고루틴이 수만 개면 그 재스캔 자체가 새로운 STW 병목이 된다.

Go 1.8 은 그 재스캔을 없애기 위해 Yuasa 삭제 배리어를 섞었다. 덮어쓰기 전의 옛 값을 shade 하면, 스택에서 포인터가 사라지기 전에 힙에서 원본이 지워지는 경우를 잡을 수 있다. 여기에 "내 스택이 아직 회색일 때만 새 값도 shade 한다"는 조건부 삽입 조항을 붙이면, 스택이 검게 스캔된 뒤에는 삽입 쪽 추가 비용이 사라진다. 버려진 대안은 다음과 같다. 참조 카운팅은 순환을 못 걷고 모든 쓰기에 원자적 증가/감소를 요구해 처리량을 갉아먹는다. 이동식 압축 수집기는 읽기 배리어를 요구하는데, 포인터를 자주 읽는 Go 코드에서 읽기마다 비용을 물리는 것은 쓰기마다 무는 것보다 훨씬 비싸다. 세대별 수집기는 기억 집합(remembered set)을 유지해야 해서 결국 배리어가 더 필요하고, Go 는 이스케이프 분석으로 상당량을 스택에 두기 때문에 세대 구분의 이득이 실측으로 잘 나오지 않았다. 결국 Go 는 지금도 비이동식, 비세대별, 동시 마크-스윕 수집기이고, 그 중심에 hybrid 배리어가 있다.

## 어떻게 동작하는가

색은 저장되는 필드가 아니다. 흰색은 `mspan` 의 `gcmarkBits` 에서 해당 비트가 0 인 상태다. 회색은 마크 비트는 섰지만 그 객체의 포인터가 아직 `workbuf` 큐에 남아 있는 상태다. 검정은 마크 비트가 서고 큐에서 빠져 자식까지 전부 shade 된 상태다. 즉 회색은 객체의 속성이 아니라 "작업 큐에 있다"는 관계다. 작업 큐는 `workbuf` 라는 객체들의 연결 리스트이고, 각 P 는 `gcWork` 를 통해 `work.full` 과 `work.empty` 목록에서 `workbuf` 를 빌려 쓴다. `gcw.put` 은 꽉 찬 버퍼를 `work.full` 에 넘기고, `gcw.tryGet` 은 `work.empty` 에서 빈 버퍼를 가져온다.

마킹은 `gcStart` 가 `gcphase` 를 `_GCmark` 로 올리면서 시작한다. 이때 전역 변수, 스택, 전역 자료 구조가 루트로 처리된다(`markroot`). 각 고루틴의 스택은 안전 지점에서 한 번 스캔되고, 그 뒤로는 다시 스캔되지 않는다. 이것이 1.8 이후의 계약이고, 그래서 배리어가 중요하다. 스택 스캔은 프레임별 `stackmap`(비트 벡터)을 사용해 정확하게 포인터 위치만 본다. 새 객체는 `alloc` 경로의 `gcmarknewobject` 가 즉시 마크 비트를 세워 검게 만든다. 자식이 아직 없으므로 큐에 넣을 필요도 없다. 그래서 할당 경로에는 배리어가 없고, 대신 마킹 중에 만든 객체는 이번 사이클에 회수되지 않는다.

포인터 쓰기가 일어나면 컴파일러가 미리 심어 둔 코드가 실행된다. 먼저 전역 `writeBarrier.enabled` 를 검사하고, 꺼져 있으면 한 번의 분기로 끝난다. 켜져 있으면 `runtime.gcWriteBarrier` 변형(amd64 기준 `gcWriteBarrier2` 등)을 호출해 (슬롯 주소, 쓴 값) 쌍을 현재 P 의 `wbBuf` 에 밀어 넣는다. `wbBuf` 는 순차 저장 버퍼(sequential store buffer)의 변형으로, 버퍼가 차면 `wbBufFlush` 가 이를 `gcWork` 로 옮긴다. 이때 슬롯에 대해 옛 값을 shade 하는 것이 삭제 배리어 쪽 일이고, 스택이 아직 회색인 구간에서는 새 값도 함께 shade 한다. 버퍼를 쓰는 이유는 배리어 호출 지점에서 곧바로 작업 큐를 건드리면 락 경합과 캐시 미스가 터지기 때문이다. 쌍을 모아 두고 한 번에 처리하면 배리어 자체는 저장 두 번과 포인터 증가로 끝난다.

마킹이 끝나면 `gcMarkDone` 이 남은 작업을 소진하고 `gcMarkTermination` 이 세계를 아주 짧게 멈춰 상태를 `_GCoff` 로 되돌린다. 스윕은 다시 동시에 진행되며, `mspan` 의 `gcmarkBits` 와 `allocBits` 를 비교해 살아있는 객체를 표시하고 나머지를 프리 리스트로 돌려준다. 배리어가 지켜야 하는 불변식은 이 마지막 스윕이 "살아있는 객체의 비트는 반드시 서 있다"는 것 하나로 요약된다.

## 돌려보기

```bash
go vet ./...                 # 정적 검사: printf 포맷과 사용하지 않는 값이 없는지
go build -o /dev/null ./...  # 컴파일 확인: 배리어 관련 코드가 실제로 빌드되는지
go run .                     # 시연 실행: 1~4번 절의 표와 수치를 본다
go test -v ./...             # 테스트: 배리어별 lost 기대값이 표와 일치하는지
go test -race ./...          # 동시성 주제이므로 반드시: GC 하머 고루틴과 쓰기 루프가 경합하지 않는지
go test -bench=. -benchmem ./...   # 포인터 쓰기 vs 정수 쓰기 벤치마크
GODEBUG=gctrace=1 go run .         # 각 GC 사이클의 마킹/스윕 시간과 힙 크기를 본다
GODEBUG=gccheckmark=1 go run .     # 런타임이 마킹 불변식을 직접 재검사한다(패닉 없으면 통과)
GOMAXPROCS=1 go run .              # P 가 하나면 마킹이 쓰기 루프와 겹쳐 4번 절 비율이 커진다
```

`go run .` 에서 1번 절은 시뮬레이터 표, 2번 절은 실제 어셈블리 조각, 3번 절은 STW 정지 시간 목록, 4번 절은 조건별 ns/op 를 출력한다. `GODEBUG=gccheckmark=1` 은 마킹 종료 시 모든 루트와 스택을 다시 훑어 흰 객체를 가리키는 참조가 있는지 검사하는 모드다. 시연 프로그램이 정상이라면 아무 일도 일어나지 않고, 만약 배리어에 구멍이 있다면 여기서 패닉이 난다.

## 코드로 확인하기

1번 절 표의 열을 읽는 법부터. `result` 가 `LOST` 면 실제로 살아있는 객체가 흰색으로 남아 회수된 것이고, 이는 런타임에서 use-after-free 다. `shades` 는 배리어가 shade 를 호출한 횟수(이미 회색이나 검정이어도 검사 비용은 든다), `scans` 는 스택을 훑은 횟수, `floating` 은 죽었는데 이번 사이클에 못 걷은 객체 수다. S3(회색 스택)에서 `delete` 가 LOST 를 내는 이유는 지역 변수 쓰기에 배리어가 없기 때문이고, S4(검은 스택)에서 `insert` 가 LOST 를 내는 이유는 힙에서의 삭제를 삽입 배리어가 보지 않기 때문이다. 두 줄이 정확히 대칭이고, `hybrid` 만 두 곳 모두에서 ok 다. 마지막 요약에서 `none` 은 5개 중 3개, `insert` 와 `delete` 는 각각 1개, `hybrid` 와 `insert+rescan` 은 0개 시나리오에서 객체를 잃는다.

`insert+rescan` 이 0 인데도 Go 가 채택하지 않은 이유는 `scans` 열에 있다. 이 모드는 마킹이 끝날 때 스택을 한 번 더 훑는다. 고루틴 1만 개에 스택 2KB 면 20MB 를 세계를 멈춘 채 훑어야 하고, 이 비용은 힙 크기가 아니라 고루틴 수에 비례한다. 그래서 "힙이 커져도 정지 시간은 그대로"라는 목표와 정면으로 충돌한다.

2번 절은 `go tool compile -S` 로 뽑은 어셈블리에서 `gcWriteBarrier` 문자열을 세어 보여 준다. 포인터를 쓰는 함수에서는 등장하고, 정수만 쓰는 함수에서는 0회다. 함께 찍히는 `CMPB runtime.writeBarrier(SB)` 와 그 뒤의 조건 점프가 "GC 가 꺼져 있을 때의 빠른 경로"다. 배리어 비용은 대부분 이 분기 하나로 흡수되고, 실제 버퍼링은 마킹 중에만 일어난다.

3번 절은 살아있는 힙을 7MB 남짓 만들어 놓고 6번 GC 를 돌려 각 정지 시간을 마이크로초로 찍는다. 힙이 7MB 인데 정지가 수십 마이크로초 수준으로 나오는 것이 정상이고, 이 수치는 힙을 두 배로 키워도 크게 변하지 않는다. 마킹이 뮤테이터와 같이 돌기 때문에 정지 구간에는 상태 전환만 남기 때문이다. 4번 절은 같은 쓰기 루프를 네 조건에서 재서 배리어 몫을 대략 분리한다. 정수 쓰기와 포인터 쓰기를 같은 GC 압력 아래에서 비교하는 이유는, 마킹이 P 시간을 가져가는 몫이 양쪽에 똑같이 들어가서 차이를 빼면 사라지기 때문이다.

`main_test.go` 는 시뮬레이터의 주장을 숫자로 고정한다. hybrid 가 모든 시나리오에서 lost 0 이고 회색 객체를 남기지 않는다는 것, S3/S4 에서 각 배리어가 정확히 기대한 곳에서만 실패한다는 것, insert+rescan 이 스택을 정확히 두 번 훑는다는 것, 마킹 중 할당이 즉시 검정이라는 것, 그리고 마킹 중에 죽은 객체가 이번 사이클에 회수되지 않는다는 것을 검증한다.

## 모르면 겪는 일

가장 흔한 사고는 포인터를 `uintptr` 에 담아 두는 것이다. `unsafe.Pointer` 를 `uintptr` 로 바꿔 구조체 필드나 맵 값에 저장하면, GC 는 그 값을 포인터로 보지 않는다. 다른 참조가 모두 사라진 순간 객체는 회수되고, 나중에 그 정수를 포인터로 되돌리면 해제된 메모리를 읽는다. 증상은 저장 지점에서 한참 떨어진 곳에서 나는 알 수 없는 값 손상이나, 극히 낮은 확률로만 재현되는 크래시다. 같은 이유로 `syscall.Syscall` 에 넘긴 포인터는 호출이 끝날 때까지 살아있다는 보장이 없어서 `runtime.KeepAlive` 가 필요하다.

두 번째는 "분명히 nil 로 만들었는데 메모리가 안 줄어든다"는 증상이다. 큰 트리를 참조하던 맵 엔트리를 마킹 도중에 지우면, hybrid 배리어의 삭제 절반이 그 루트를 shade 해서 이번 사이클에는 살려 둔다. `HeapAlloc` 은 다음 GC 때까지 내려가지 않고, 컨테이너 메모리 한도가 빡빡하면 그 한 사이클 사이에 OOM 이 난다. 같은 이유로 마킹 중에 만든 큰 버퍼는 즉시 검정이라 이번 사이클에 절대 안 걷힌다. 초당 수 GB 를 할당하며 대부분을 곧바로 버리는 워크로드에서 RSS 가 살아있는 힙의 두 배로 튀는 이유가 이것이다.

세 번째는 p99 스파이크인데 CPU 프로파일에는 잘 안 보이는 종류다. 포인터를 힙에 많이 쓰는 뜨거운 루프(그래프 순회, 큰 맵 갱신, 연결 리스트 조립)가 있으면, 마킹이 도는 동안 그 루프의 모든 저장이 per-P 버퍼를 채우고 주기적으로 `wbBufFlush` 를 유발한다. 버퍼가 비는 순간 작업 큐로 밀어 넣는 비용이 한꺼번에 붙어서, 평균은 멀쩡한데 마킹 구간에만 지연이 튄다. 이때 해법은 배리어를 없애는 것이 아니라 자료 구조를 바꾸는 것이다. 포인터 슬라이스 대신 값을 담은 슬라이스를 쓰면 그 쓰기들은 배리어 대상에서 빠진다.

네 번째는 스택 재스캔과 혼동하는 경우다. 고루틴을 수십만 개 띄우면 GC 가 느려질 것 같지만, 1.8 이후로는 스택 재스캔이 없으므로 마킹 종료 정지는 고루틴 수에 크게 좌우되지 않는다. 대신 스택 자체가 루트로 스캔되므로 살아있는 고루틴이 많으면 마킹해야 할 루트가 늘고, 회색 큐 작업량이 늘어 전체 GC 사이클 시간이 길어진다. 정지 시간이 아니라 총 처리량이 줄어드는 방향이다.

## 언제 신경 쓰고 언제 무시하나

살아있는 힙이 수백 MB 이하이고 p99 에 민감하지 않은 서비스라면 이 주제는 사실상 무시해도 된다. 배리어 비용은 포인터 쓰기 한 번에 몇 나노초 수준이고, 정지 시간은 수십 마이크로초라 사용자 지연에 묻힌다. 이때 최적화할 것은 배리어가 아니라 할당량이다. `GOGC` 를 올려 GC 빈도를 줄이는 편이 훨씬 큰 효과를 낸다.

신경 써야 하는 조건은 세 가지다. 첫째, 포인터를 힙에 쓰는 비율이 매우 높은 워크로드. 예를 들어 `map[string]*Item` 을 초당 수백만 번 갱신하거나, 포인터로 이어진 큰 그래프를 계속 재배선하는 코드다. 이때는 값을 담는 구조로 바꾸는 것만으로 마킹 중 지연이 눈에 띄게 줄어든다. 둘째, 컨테이너 메모리 한도가 살아있는 힙의 두 배 안쪽으로 조여진 환경. 삭제 배리어가 남기는 부동 쓰레기와 마킹 중 할당이 겹치면 순간 RSS 가 한도의 위로 올라간다. `GOMEMLIMIT` 과 `GOGC` 를 함께 조정해야 한다. 셋째, GC 사이클 시간 자체가 문제인 경우. 힙이 수 GB 를 넘어가면 정지는 작아도 마킹에 걸리는 총시간이 길어져 CPU 를 상시로 잡아먹는다.

무시해도 되는 것은 배리어의 어셈블리 수준 세부다. `gcWriteBarrier` 가 어떤 레지스터를 쓰는지, `wbBuf` 크기가 몇인지는 런타임 구현 세부이고 버전마다 바뀐다. 알아야 할 것은 두 가지뿐이다. 포인터를 힙에 쓰는 지점에는 항상 훅이 있고, 그 훅은 GC 가 마킹 중일 때만 실제로 일을 한다. 그리고 마킹 중에 할당하거나 참조를 끊은 객체는 이번 사이클에 정리되지 않는다.
