## 한 줄 요약

`alloc_space` 는 "태어난 뒤 지금까지 만든 양", `inuse_space` 는 "지금 살아 있는 양"이다. 누수는 `inuse_space` 로 찾고, 과다 할당은 `alloc_space` 로 찾는다. 둘 다 표본 추출로 만들어진 추정치라서, 추출 간격(`runtime.MemProfileRate`, 기본 512 KiB)이 측정 대상보다 크면 숫자가 0 이 되거나 몇 배로 튄다.

## 왜 이런 설계인가

메모리 프로파일의 근본 문제는 "모든 할당을 정확히 기록하면 프로그램이 느려진다"는 것이다. 할당 한 번마다 콜스택을 32 프레임까지 걷고, 그 스택을 해시해서 버킷을 찾고, 카운터를 갱신해야 한다. 작은 객체를 초당 수백만 개 만드는 프로그램에서는 이 비용이 실제 작업 비용보다 커진다. 초기 Go 는 실제로 전수 기록에 가까운 방식을 썼지만, 할당이 잦은 서버에서는 프로파일을 켜는 순간 처리량이 눈에 띄게 떨어졌다. 그래서 지금은 "확률 표본"을 기본으로 한다.

대안은 세 가지였다. 첫째, 정확한 누적 계수만 유지하는 방법(`MemStats.TotalAlloc`)이다. 이건 지금도 존재하고 표본 오차가 전혀 없지만, "어느 코드가 만들었는가"라는 정보가 없다. 누수를 찾는 데는 쓸 수 없다. 둘째, 전수 기록이다. 정확하지만 위에서 말한 비용 때문에 상시 사용이 불가능하다. 셋째, 채택된 방식인 크기 비례 확률 표본이다. 객체가 표본으로 잡힐 확률을 그 크기에 비례하게 만들어, 큰 객체는 거의 항상 잡고 작은 객체는 드물게 잡는다.

크기 비례로 만든 이유가 중요하다. 균등 확률로 표본을 뽑으면, 1 KiB 객체 100 만 개와 1 MiB 객체 1000 개가 표본에서 비슷한 무게를 갖게 되어 큰 객체가 만드는 압력을 놓친다. 크기 비례로 뽑으면 "표본 하나가 대표하는 바이트 수"가 거의 일정해지고, 그 덕분에 단순한 역산 계수 하나로 전체를 복원할 수 있다. 이 계수가 pprof 가 화면에 보여주는 값과 원자료의 차이다.

`inuse` 를 따로 유지하는 것도 같은 이유의 연장이다. `alloc` 만 쌓으면 "지금 메모리를 붙잡고 있는 범인"을 알 수 없다. 힙 크기는 누적 할당량이 아니라 살아 있는 객체의 합이기 때문이다. 그래서 런타임은 할당 시점에 버킷에 `allocBytes` 를 더하고, 해제 시점에 같은 버킷에 `freeBytes` 를 더한다. 두 값의 차이가 사이트별 `inuse` 이고, 이걸 스택별로 정렬한 것이 `-inuse_space` 뷰다.

## 어떻게 동작하는가

할당 경로부터 보자. `runtime/malloc.go` 의 `mallocgc` 안에는 이런 갈래가 있다. 현재 `m` 의 `mcache` 에 있는 `nextSample` 필드에서 "다음 표본까지 남은 바이트"를 빼면서 진행하다가, 그 값이 바닥나면 `profilealloc` 을 부른다. `profilealloc` 은 `nextSample()` 로 다음 간격을 뽑는데, 이 함수가 지수분포를 쓴다. 지수분포를 쓰는 이유는 표본 개수가 푸아송 분포를 따르게 되어 통계적 해석이 쉬워지기 때문이다. 이 시점에 `mProf_Malloc` 이 호출되어 `runtime/mprof.go` 의 `stkbucket` 으로 스택별 버킷을 찾고, `allocBytes` 와 `nmalloc` 을 갱신한다.

해제 경로는 `mProf_Free` 다. 같은 버킷에 `freeBytes` 와 `nfree` 를 더한다. 여기서 중요한 성질이 하나 나온다. `alloc` 은 단조 증가하지만 `inuse` 는 줄어들 수 있다는 것, 그리고 사이트별로 `AllocBytes - FreeBytes` 를 계산하면 "그 코드가 지금 붙잡고 있는 양"이 된다는 것이다.

`runtime.MemProfile` 은 이 버킷들을 `MemProfileRecord` 슬라이스로 바꾼다. 이때 레코드에 들어가는 값은 **표본으로 잡힌 크기의 합**이지 추정치가 아니다. 여기가 가장 많이 오해되는 지점이다. 예를 들어 4096 바이트 객체를 8 MiB 만들고 추출률이 512 KiB 라면, 표본은 평균 16 개 잡히고 레코드의 합은 약 64 KiB 로 나온다. 실제 할당량의 100 분의 1 도 안 되는 숫자다.

그래서 pprof 가 역산을 한다. 객체가 잡힐 확률이 크기에 비례한다는 사실에서 평균 크기 `avgSize` 의 포함 확률 `p = 1 - exp(-avgSize/rate)` 를 구하고 `1/p` 를 곱한다. 위 예에서 `p` 는 약 0.0078 이므로 계수가 약 128 이 되고, 64 KiB 가 8 MiB 로 복원된다. 이 함수가 pprof 내부의 `scaleHeapSample` 이며, `main.go` 의 `scaleRawSample` 이 같은 식을 구현해 둔 것이다. 계수는 레코드마다 평균 크기가 다르므로 레코드마다 따로 계산된다.

출력 형식은 두 가지다. `pprof.Lookup("heap").WriteTo(w, 0)` 은 protobuf 이고 `go tool pprof` 가 먹는 형식이며, `WriteTo(w, 1)` 은 사람이 읽는 텍스트다. 텍스트 첫 줄이 `heap profile: inuse객체: inuse바이트 [alloc객체: alloc바이트] @ heap/추출률` 이다. 두 경로 모두 시작할 때 `runtime.GC()` 를 강제한다. `inuse` 를 세려면 죽은 객체를 먼저 회수해야 하기 때문이고, 그 대가로 STW 가 한 번 발생한다. `runtime.ReadMemStats` 도 같은 이유로 STW 를 유발한다.

## 돌려보기

```bash
go vet ./...                 # 정적 검사: 표본 관련 상수나 포맷 문자열 오타를 잡는다
go build -o /dev/null ./...  # 컴파일 확인
go run .                     # 시연 실행: 4개 절의 수치를 눈으로 비교한다
go test -v ./...             # 테스트: 불변식(alloc 증가, inuse 불변 등)을 검증
go test -race ./...          # 동시성 주제이므로 반드시: 전역 추출률 조작이 안전한지 확인
go test -bench . -benchmem ./...  # 프로파일 한 장의 가격을 나노초로 확인
```

`go run .` 에서 볼 것은 네 가지다. 첫째, 버리기 루프에서 `TotalAlloc` 은 8 MiB 넘게 늘어나는데 `HeapAlloc` 은 거의 그대로인지. 둘째, 같은 8 MiB 를 붙잡으면 `HeapAlloc` 이 그만큼 올라가고 참조를 놓으면 다시 내려오는지. 셋째, 추출률 표에서 `원자료` 열이 `정확값` 열보다 항상 작고 `pprof보정` 열이 그걸 메우는지. 넷째, `mem.prof` 파일이 생기고 `go tool pprof -inuse_space mem.prof` 로 열리는지.

`go test -race` 에서는 전역 `runtime.MemProfileRate` 를 만지는 코드가 있으므로, 측정 구간에 다른 goroutine 이 할당을 하지 않는지 확인해야 한다. 이 저장소의 테스트는 측정 창 안에서 단일 goroutine 만 할당한다.

## 코드로 확인하기

`demoChurn` 은 8 MiB 를 만들고 즉시 버린다. 출력에서 `TotalAlloc +8388608` 근처의 값과 `HeapAlloc` 의 변화 없음이 같이 나온다. 프로파일 원자료의 `alloc` 증가분은 그보다 훨씬 작은 값(대략 6 만 바이트대)인데, 이는 표본이 16 개쯤 잡혔고 각 표본이 4096 바이트였기 때문이다. 즉 원자료는 "표본의 합"이라는 사실이 숫자로 드러난다. `inuse` 증가분은 0 근처다. 버린 객체는 GC 뒤에 `freeBytes` 로 상쇄되기 때문이다.

`demoLeakVsChurn` 은 같은 8 MiB 를 한 번은 버리고 한 번은 전역 슬라이스에 매단다. `alloc` 기준으로는 두 경우가 거의 같다. 갈라지는 것은 `inuse` 와 `HeapAlloc` 이다. 붙잡은 쪽만 `HeapAlloc` 이 8 MiB 넘게 올라가고, 프로파일 `inuse` 도 따라서 올라간다. 참조를 놓은 뒤의 `HeapAlloc` 이 다시 내려오는 것까지가 한 세트다. 이 세 줄이 "누수 판정은 inuse 로" 의 근거다.

`demoRates` 는 같은 작업을 추출률만 바꿔 네 번 잰다. 추출률 1 에서는 원자료가 정확값과 거의 같고(비율 약 1.0), 64 KiB 에서는 비율이 0.1 아래로 떨어지며, 512 KiB 에서는 0.01 수준, 8 MiB 에서는 표본이 0 개라 원자료가 0 이 된다. 마지막 열의 `pprof보정` 값은 원자료에 역산 계수를 곱한 것으로, 표본이 1 개라도 있으면 정확값 근처로 돌아온다. 표본이 0 개면 곱할 대상이 없어 0 이라는 점이 이 표의 핵심 교훈이다.

`main_test.go` 는 이 관계들을 불변식으로 고정한다. `TestAllocVsInuse` 는 정확값 기준으로 할당이 실제로 일어났고 GC 뒤에 살아 있지 않음을 확인한다. `TestLeakVsChurn` 은 붙잡은 쪽의 `HeapAlloc` 과 프로파일 `inuse` 가 모두 커져야 한다고 요구한다. `TestSamplingAccuracyAtRateOne` 은 추출률 1 에서 원자료와 정확값의 비율이 0.5 에서 2 사이인지 본다. `TestSamplingGranularity` 는 1 MiB 간격으로 256 KiB 를 재면 정확값 근처에 올 수 없다는 것만 확인한다(표본이 0 개인 경우도 통과로 처리한다). `TestProfileDisabled` 는 추출률 0 에서 표본이 정확히 0 이 되는지, 그래도 실제 할당은 일어나는지 본다. `TestScaleRawSample` 은 역산 계수의 성질(추출률 1 이면 보정 없음, 표본 0 이면 0)을 고정한다.

## 모르면 겪는 일

가장 흔한 증상은 "`-alloc_space` 상위에 뜬 함수를 보고 누수라고 보고하는 것"이다. JSON 응답을 만들 때마다 임시 버퍼를 만드는 핸들러는 `alloc_space` 에서 항상 1 등이다. 하지만 GC 뒤에 `inuse_space` 를 보면 아무것도 남지 않는다. 이걸 구분하지 못하면 멀쩡한 코드를 "누수"라며 리팩터링하고, 진짜 누수는 놓친다. 진짜 누수는 `alloc` 이 계속 늘면서 `inuse` 도 같이 우상향하는 모양을 보인다.

두 번째는 추출률 때문에 생기는 착시다. 라이브러리나 테스트 프레임워크가 `runtime.MemProfileRate` 를 0 으로 만들어 둔 상태에서 프로파일을 뜨면 파일이 비어 있고, 그 0 을 "누수 없음"으로 읽는다. 반대로 아주 큰 추출률을 쓰면 몇십 MB 를 할당해도 표본이 0 개라 `inuse` 가 0 으로 보인다. 또 추출률을 바꾼 직후에는 `mcache` 의 `nextSample` 카운터가 남아 있어서, 한동안 표본이 하나도 안 잡히는 구간이 생긴다. 큰 추출률로 실험한 뒤의 측정값이 이상하게 작다면 이 카운터를 의심해야 한다.

세 번째는 프로파일 자체의 비용을 잊는 것이다. 힙 프로파일 한 장은 GC 를 강제하고, `runtime.ReadMemStats` 도 STW 를 유발한다. 이걸 10 초마다 도는 모니터링에 넣으면, CPU 프로파일에는 아무것도 안 보이는데 p99 지연만 주기적으로 튀는 현상이 생긴다. 원인을 찾으려고 다시 프로파일을 켜면 증상이 심해지고, 프로파일에는 GC 와 프로파일 코드만 잡히는 악순환이 된다.

네 번째는 표본 오차를 신뢰 구간 없이 읽는 것이다. 8 MiB 를 재는데 표본이 16 개라면, 추정치의 상대 오차는 대략 25 퍼센트다. 두 시점의 `inuse` 차이가 20 퍼센트라면 그건 누수가 아니라 잡음일 수 있다. 반대로 힙이 수 GB 인 서비스에서 기본 추출률 512 KiB 는 충분히 촘촘하다. 문제는 큰 힙이 아니라, 힙은 작은데 할당률이 매우 높은 프로그램이다. 이때는 `inuse` 스냅샷 몇 장으로는 안 보이고, `alloc` 추세를 보거나 추출률을 낮춰야 한다.

## 언제 신경 쓰고 언제 무시하나

힙이 수십 MB 이하이고 프로세스 수명이 짧은 배치라면 이 주제에 시간을 쓸 이유가 거의 없다. 기본 추출률로도 큰 객체는 잘 잡히고, 메모리 문제가 있으면 프로세스가 그냥 죽거나 눈에 띄게 느려진다. 이 규모에서는 `alloc_space` 와 `inuse_space` 의 차이를 외우고 있을 필요도 없고, 필요할 때 한 번 떠 보면 된다.

신경 써야 하는 조건은 세 가지다. 첫째, 힙이 수백 MB 를 넘고 시간에 따라 우상향한다. 둘째, 할당률이 초당 수십 MB 를 넘어 GC 압력이 처리량을 지배한다. 셋째, p99 지연이 주기적으로 튀는데 CPU 프로파일에 원인이 안 보인다. 이 세 경우에만 `-inuse_space` 와 `-alloc_space` 를 번갈아 보면서 추세를 비교할 가치가 있다.

과최적화 방지선도 분명히 해 두자. `inuse` 수치가 두 배 차이 난다고 코드를 고치지 마라. 표본 오차와 측정 시점 차이로 그 정도는 얼마든지 흔들린다. 판단은 절대값이 아니라 여러 번 떠서 얻은 추세로 하고, 최소한 세 번 이상 같은 방향으로 움직이는지 확인하는 편이 좋다. 또한 추출률을 낮춰 정밀도를 올리는 것은 그 자체로 오버헤드이므로, 진단하는 동안에만 쓰고 평상시 설정으로 되돌려야 한다.
