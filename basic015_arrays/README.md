> `vet: ./main.go:14:57: cannot convert a (variable of type [3]int) to type []int`  

## 한 줄 요약

Go에서 `배열`은 길이가 타입의 일부이고 값 타입이라 넘길 때마다 통째로 복사됩니다. 그래서 일상에서는 슬라이스를 씁니다.

## 왜 필요한가

다른 언어(Python, JavaScript, Java)에서 "배열"은 보통 가변 길이이고 참조로 전달됩니다. Java의 `int[]`도 참조 타입이고, Python의 `list`도 참조 semantics입니다. Go는 이 둘을 명확히 나눕니다.

첫째, Go의 **배열 타입에는 길이까지 포함**됩니다. `[3]int`와 `[4]int`는 서로 다른 타입이라 한 함수에서 둘 다 받아들이는 것은 불가능합니다. 이것이 Go가 "왜" 그런가 — 컴파일 단계에서 데이터 구조의 크기를 고정시킴으로써 루프 회전(unroll) 등 최적화를 쉽게 하고, 메모리 레이아웃을 확정짓기 위함입니다.

둘째, Go 배열은 **값 타입**입니다. 함수 인자로 넘기면 배열 전체가 복사됩니다. Java에서는 배열 참조만 복사되어 원본이 바뀔 수 있지만, Go에서는 원본이 바뀌지 않습니다. 이 차이는 Go가 "가벼운 값"과 "가벼운 참조"를 명확히 분리하려는 설계 의도입니다.

일상적으로 슬라이스를 쓰는 이유는 이 두 속성 때문입니다. 배열은 함수 시그니처를 길이로 구속하고, 넘길 때마다 메모리/시간 비용이 듭니다. 슬라이스는 이 둘을 모두 없앱니다 — 길이가 타입에 포함되지 않아 함수가 모든 길이를 받고, underlying array를 공유하므로 복사 비용도 없습니다.

## 기본 사용

```go
var a [3]int          // 길이 3, 초기값 0
a = [3]int{1, 2, 3}  // 리터럴
```

배열 리터럴에서 길이를 생략하면 컴파일러가 추론합니다.

```go
a := [...]int{1, 2, 3} // 길이 3으로 추론
```

배열을 슬라이스로 변환하려면 캐스트와 다릅니다. Go는 명시적 변환 구문을 씁니다.

```go
s := []int(a) // [3]int → []int
```

배열끼리 `==` / `!=` 비교가 가능합니다. 슬라이스는 비교할 수 없습니다.

## 돌려보기

```bash
go vet ./...      # 정적 검사 — 컴파일 오류 없음을 확인
go run .          # 시연 실행 — 배열 복사 vs 슬라이스 공유 출력 비교
go test -v ./...  # 테스트 — 3개 테스트 통과 확인
```

`go vet`은 변수 미사용, 타입 불일치 등을 잡아냅니다. `go run .` 출력에서 `before:`가 배열은 변하지 않고 슬라이스는 변하는 것을 눈으로 확인하세요. `go test`는 세 테스트를 모두 통과해야 합니다.

## 실전에서는 이렇게 쓴다

**1. 고정 크기 레코드 고정 배열 사용**

```go
type Point [2]float64

func dist(a, b Point) float64 { ... }
```

길이가 타입에 포함되므로 `dist([2]float64, [2]float64)`만 받고 `[3]float64`는 아예 컴파일 단계에서 걸러집니다. 2차원 좌표처럼 크기가 정말 고정된 데이터에 유용합니다.

**2. 슬라이스 반환 함수에서 내부 버퍼로 배열 사용**

```go
func ReadAll(r io.Reader) ([]byte, error) {
    var buf [4096]byte
    n, err := r.Read(buf[:])
    return buf[:n], err
}
```

여기서 `buf`는 스택에 할당되는 배열이지만, 반환할 때는 슬라이스 `buf[:n]`로 잘라내어 underlying array만 공유합니다. 배열은 복사되지 않고 슬라이스 header만 반환됩니다. 표준 라이브러리가 실제로 쓰는 패턴입니다.

**3. 함수 포인터 테이블 고정 배열**

```go
var handlers [256]func([]byte)
```

배열 인덱스로 바로 접근하는 테이블은 슬라이스보다 약간 빠릅니다. 런타임에 길이가 변하지 않는 테이블이면 배열을 쓰는 경우가 있습니다.

## 흔한 실수

### 1. 배열을 슬라이스 인자에 그대로 넘기기

```go
// 틀린 코드
func takesSlice(s []int) {}
a := [3]int{1, 2, 3}
takesSlice(a) // 컴파일 오류: cannot use a (type [3]int) as type []int
```

`[3]int`와 `[]int`는 다른 타입입니다. Go는 암묵 변환을 허용하지 않습니다.

**어떤 일이 벌어지는지** — 컴파일러가 다음과 같은 메시지를 출력합니다.

```
cannot use a (variable of type [3]int) as type []int in argument to takesSlice
```

**왜 그런지** — Go는 타입을 엄격하게 구분합니다. 배열과 슬라이스는 내부 구조가 다릅니다. 배열은 길이가 타입에 포함되는 값이고, 슬라이스는 헤더(포인터·길이·용량)입니다.

**고친 코드**

```go
takesSlice(a[:]) // 슬라이스로 잘라넘기기
```

### 2. 슬라이스를 배열 인자에 넘기기

```go
// 틀린 코드
func takesArray(a [3]int) {}
s := []int{1, 2, 3}
takesArray(s) // 컴파일 오류
```

반대 방향도 안 됩니다. 슬라이스를 배열에 넘기려면 요소 하나씩 복사해야 합니다.

```go
for i := range s {
    a[i] = s[i]
}
takesArray(a)
```

이건 귀찮으니 그냥 배열 대신 슬라이스를 쓰는 게 낫습니다.

### 3. 배열을 넘겼는데 "왜 원본이 안 바뀌지?" 하고 당황하기

```go
func mutateArray(a [3]int) [3]int {
    a[1] = 99
    return a
}
```

이 코드는 "버그"가 아닙니다. Go 배열은 값 전달이라 원본이 안 바뀌는 게 **정상 동작**입니다. Java나 Python 개발자가 이걸 "왜 안 바뀌지?"라고 생각하면 됩니다.

**어떤 일이 벌어지는지** — `mutateArray` 안의 `a`는 `before`의 복사본입니다. `before`는 변하지 않습니다.

**왜 그런지** — Go는 배열을 값 타입으로 설계했습니다. 복사 비용은 있지만 의도치 않은 수정을 방지합니다.

**고친 코드** — 원본을 바꾸고 싶으면 슬라이스를 쓰세요.

```go
func mutateSlice(s []int) {
    s[1] = 99
}
```

### 4. 배열 리터럴 길이 생략을 모르고 컴파일 오류 내기

```go
// 틀린 코드
var a [3]int = {1, 2, 3} // 컴파일 오류
```

Go는 배열 리터럴에서 길이 생략을 허용하지만, `var` 선언과 함께 쓸 때는 `[]`가 아닙니다. `...`을 써야 합니다.

```go
var a [3]int = [3]int{1, 2, 3}  // 명시적 길이
a := [...]int{1, 2, 3}          // 추론
```

**어떤 일이 벌어지는지** — `syntax error: unexpected {, expecting type` 같은 메시지가 뜹니다.

**왜 그런지** — Go는 리터럴 구문을 명확히 구분합니다. 배열 리터럴은 `[n]T{...}` 형태여야 합니다.

## 주의할 점

**1. 배열은 스택에 할당될 가능성이 높다**

작은 배열은 함수의 스택 프레임에 할당됩니다. Java 배열은 항상 힙입니다. Go 컴파일러는 배열이 함수를 빠져나갈 때 힙으로 밀어 올릴 수도 있지만, 일반적으로 작은 배열은 스택에 남습니다. 이는 메모리 레이아웃을 예측 가능하게 만듭니다.

**2. 배열 비교는 모든 요소를 비교한다**

```go
a := [3]int{1, 2, 3}
b := [3]int{1, 2, 3}
fmt.Println(a == b) // true
```

슬라이스는 `==` 비교 자체가 컴파일 오류입니다. 슬라이스 동등 비교는 `reflect.DeepEqual`이나 수동 루프를 써야 합니다.

**3. 배열은 `len`과 `cap`이 같다**

배열의 길이는 고정입니다. `cap(a)`는 `len(a)`와 항상 같습니다. 슬라이스와 달리 `cap`으로 추가 공간을 확보할 수 없습니다. `append`는 배열에 적용할 수 없습니다 — 슬라이스에만 적용됩니다.

**4. Go 1.22+ 루프 변수 공유 문제**

배열 `for range`에서 루프 변수를 클로저에capture하면 Go 1.22 이전에는 모든 클로저가 마지막 요소를 가리킵니다. Go 1.22부터는 iteration variable이 각 반복마다 새로 할당됩니다. 이 차이를 모르고 구버전을 타겟팅하면 버그가 생깁니다.

## 코드로 확인하기

`go run .` 출력을 보면:

```
길이가 같은 배열 비교: true
배열(복사본 전달): before: [10 20 30] after: [10 99 30]
슬라이스(원본 공유): before: [10 99 30] after: [10 99 30]
```

첫째 줄: 길이가 같은 배열 `a`와 `b`는 `==` 비교에서 `true`. 배열은 값 비교가 가능합니다.

둘째 줄: `before`는 여전히 `[10 20 30]`. `mutateArray`는 복사본만 바꿨습니다. `after`는 `[10 99 30]`.

셋째 줄: `before`도 `[10 99 30]`로 바뀌었습니다. `mutateSlice`는 같은 underlying array를 공유하기 때문입니다.

이 출력 차이 — `before`가 배열에서는 안 바뀌고 슬라이스에서 바뀌는 것 — 이 Go 배열 vs 슬라이스의 핵심 차이입니다.

`main_test.go`는 세 테스트로 검증합니다:

1. `TestArrayLengthIsPartOfType`: 같은 길이·값의 배열이 `==`에서 true인지
2. `TestArrayIsPassedByValue`: 배열 전달 후 원본이 안 바뀌는지, 복사본은 바뀌는지
3. `TestSliceMutatesOriginal`: 슬라이스 전달 후 원본이 바뀌는지

## 연습 문제

1. **쉬움** — 길이가 5인 배열 두 개를 선언하고, `==`와 `!=`로 비교하는 프로그램을 쓰세요. 다른 값을 넣으면 어떻게 나오는지 확인하세요. 힌트: 배열 리터럴은 `[5]int{1, 2, 3, 4, 5}` 형태입니다.

2. **중간** — 배열을 인자로 받아 각 요소를 제곱하는 함수를 배열 버전과 슬라이스 버전 두 개 쓰세요. 배열 버전은 원본을 보존하고, 슬라이스 버전은 원본을 바꿉니다. main에서 둘 다 호출하여 출력을 비교하세요. 힌트: 슬라이스 버전은 `s[i] *= s[i]` 형태로 in-place 수정하면 됩니다.

3. **어려움** — 고정 크기 2차원 배열 `type Matrix [3][3]int`를 정의하고, 행렬 곱셈 함수 `Multiply(a, b Matrix) Matrix`를 쓰세요. 배열이 값 전달이므로 반환값으로 결과를 전달하고, main에서 원본이 보존되는지 확인하세요. 힌트: 이중 for 루프로 `c[i][j] += a[i][k] * b[k][j]` 형태입니다.
