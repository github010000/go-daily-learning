## 한 줄 요약

벤치마크는 코드를 재는 도구가 아니라, 재는 행위가 대상을 바꾸는 실험이다. 컴파일러는 결과가 쓰이지 않으면 그 계산을 지우고, `testing.B` 는 `b.N` 을 스스로 정하며, 한 번씩 잰 두 값의 차이는 대개 잡음이다. 이 세 가지를 모르면 벤치마크는 조용히, 그러나 아주 그럴듯하게 거짓말을 한다.

## 왜 이런 설계인가

Go 컴파일러는 부작용이 없는 계산을 지우는 것을 최적화가 아니라 언어 계약의 일부로 본다. 어떤 값을 만들어도 아무도 읽지 않으면 그 값은 존재할 이유가 없다. 문제는 벤치마크가 정확히 그런 코드를 짜게 만든다는 점이다. 측정하려는 대상의 결과를 어딘가에 써야 하는데, 그 "어딘가"가 없으면 측정 대상 자체가 사라진다. C 나 C++ 진영은 `asm volatile("" : : "r"(x))` 같은 인라인 어셈블리 훼이크로 이 문제를 푼다. Java 진영은 JMH 의 `Blackhole.consume` 을 쓴다. Go 는 그런 장치를 언어에 넣지 않았다. 대신 패키지 수준 변수에 쓰는 관용구 하나로 끝낸다. 패키지 수준 변수에 대한 쓰기는 다른 goroutine 이 관측할 수 있는 효과이고, 컴파일러는 관측 가능한 효과를 지울 수 없기 때문이다. `sink` 라는 이름의 전역 변수는 그래서 관습이 아니라 컴파일러 모델에 대한 정확한 대응물이다.

`b.N` 을 사용자가 정하지 않고 `testing` 패키지가 정하는 것도 같은 이유의 다른 얼굴이다. 벤치마크 대상의 비용은 수 나노초에서 수십 밀리초까지 여섯 자릿수에 걸쳐 있다. 반복 횟수를 고정하면, 아주 빠른 대상은 타이머 해상도 아래로 사라져서 0 ns/op 라는 무의미한 값이 나오고, 아주 느린 대상은 테스트 하나가 몇 분씩 걸린다. 그래서 Go 는 "목표 시간"을 기준으로 잡고 N 을 역산한다. `b.N` 은 측정 대상이 아니라 측정 도구이며, 사용자는 그 도구가 몇 번 돌든 상관하지 않고 "한 번 돌 때의 비용"만 정확히 기술하면 된다. 이 계약을 깨고 `b.N` 에 다른 의미를 부여하는 순간 벤치마크 프레임워크 전체가 무너진다.

`b.ResetTimer` 가 존재하는 이유는 벤치마크가 보통 "준비"와 "측정" 두 단계를 갖기 때문이다. 테스트 데이터를 만들고, 커넥션을 열고, 캐시를 데우는 일은 측정 대상이 아니다. 그런데 그것을 `for i := 0; i < b.N; i++` 안에 두면 ns/op 는 두 가지 일의 합이 되어버리고, 그 숫자로 두 구현을 비교하면 무엇 때문에 차이가 났는지 알 수 없다. `ResetTimer` 는 시간뿐 아니라 할당 카운터도 0 으로 되돌린다. 이 두 번째 성질이 실무에서 더 자주 문제를 일으킨다. 시간은 눈에 띄게 이상해지지만 할당 카운터는 그냥 숫자가 하나 더 붙는 것처럼 보이기 때문이다.

마지막으로 benchstat 이 존재하는 이유는, 벤치마크가 본질적으로 잡음이 많은 실험이기 때문이다. CPU 주파수 조절, 다른 프로세스, 캐시 상태, 페이지 폴트, GC 타이밍이 모두 ns/op 에 섞인다. 같은 코드를 두 번 재면 3% 에서 10% 차이가 흔하게 난다. 그런데 벤치마크를 돌리는 사람의 목적은 대개 "내 변경이 2% 빨라졌다"를 주장하는 것이다. 표본 하나씩 비교하면 그 2% 는 그냥 잡음인데도 개선이라고 보고하게 된다. benchstat 은 여러 번의 `-count` 표본을 받아 평균과 신뢰구간을 계산하고, 차이가 통계적으로 유의한지 판정한다. "측정값을 보고하는 것"과 "차이를 주장하는 것" 사이에 통계라는 완충 장치를 넣은 것이다.

## 어떻게 동작하는가

먼저 `testing.B` 의 구조를 보자. `src/testing/benchmark.go` 에 정의된 `B` 는 `common` 을 임베드하는데, `common` 에는 `N int`, `duration time.Duration`, `start time.Time`, `startAllocs uint64`, `startBytes uint64`, `netAllocs uint64`, `netBytes uint64`, `benchFunc func(*B)`, `benchTime time.Duration` 등이 들어 있다. `b.N` 은 `common.N` 이고, `b.ResetTimer` 와 `b.StopTimer` 는 모두 이 필드들을 조작한다.

실행 흐름은 이렇다. `testing.Benchmark(f)` 나 `go test -bench` 는 `b.run1()` 을 부른다. `run1` 은 먼저 `b.runN(1)` 로 한 번 재고, 목표 시간(`b.benchTime`, 기본 1초)에 도달할 때까지 N 을 기하급수적으로 키우며 `b.runN(n)` 을 반복한다. 각 `runN` 은 시작 시 `runtime.ReadMemStats` 로 `b.startAllocs` 와 `b.startBytes` 를 잡고, `b.start = time.Now()` 로 시계를 걸고, `b.benchFunc(b)` 를 호출한 뒤 `b.duration = time.Since(b.start)` 로 마감한다. 마지막에 예측한 N 으로 한 번 더 재서 최종 `BenchmarkResult` 를 만든다. 그래서 `-benchtime` 을 크게 주면 N 도 커지고 표본의 분산은 줄어든다.

`b.ResetTimer` 는 `b.start`, `b.startAllocs`, `b.startBytes` 를 현재 시점 값으로 다시 잡고 `b.duration`, `b.netAllocs`, `b.netBytes` 를 0 으로 되돌린다. `b.StopTimer` 는 그 시점까지의 경과와 `runtime.MemStats` 차이를 `netAllocs`/`netBytes` 에 누적하고 타이머를 끈다. `b.StartTimer` 는 다시 시작점을 잡는다. 여기서 주목할 점은 `StopTimer` 가 매번 `runtime.ReadMemStats` 를 부른다는 것이다. 이 호출은 전역 통계를 읽느라 상당히 비싸서, 반복문 안에서 `StopTimer`/`StartTimer` 를 부르면 측정 대상보다 계측 오버헤드가 커진다. `AllocsPerOp()` 는 `netAllocs / N`, `AllocedBytesPerOp()` 는 `netBytes / N` 을 돌려준다. 둘 다 `int64` 라는 점을 기억하자. `NsPerOp()` 도 `int64` 다. `%f` 로 찍으면 `go vet` 이 즉시 잡아낸다.

결과가 지워지는 쪽은 컴파일러 파이프라인에서 일어난다. `cmd/compile/internal/ssa` 의 deadcode 단계는 부작용이 없는 값 연산을 역방향으로 훑으며 제거한다. `string(buf)` 변환은 `slicebytetostring` 런타임 호출로 내려가는데, 그 결과가 어떤 관측 가능한 곳에도 도달하지 않으면 호출 자체가 죽은 코드로 판정된다. 반대로 `sinkStr = string(buf)` 는 전역 변수에 대한 스토어이고, 이 스토어는 다른 goroutine 이 읽을 수 있으므로 절대 지워지지 않는다. `testing.AllocsPerRun` 은 이 차이를 아주 선명하게 보여준다. 같은 변환인데 한쪽은 1 allocs/op, 다른 쪽은 0 allocs/op 가 나온다.

benchstat 의 입력은 그냥 텍스트다. `go test -bench` 의 출력을 파일로 리다이렉트해서 넘긴다. benchstat 은 각 벤치마크 이름별로 표본을 모아 평균, 중앙값, 표준편차를 계산하고 두 파일을 비교할 때는 웰치 t-검정으로 p 값을 낸다. 그리고 `p > 0.05` 이거나 효과 크기가 임계값 아래면 `~` 로 표시해서 "차이가 없다"고 말해준다. 우리 코드의 `significant` 함수는 그 골격만 축소한 것이다. 평균 차이가 합동 표준편차의 2배를 넘고, 동시에 평균의 1% 를 넘을 때만 유의하다고 본다.

## 돌려보기

```bash
go vet ./...                 # 정적 검사: printf 인자 타입이 맞는지, 특히 int64 지시자 확인
go build -o /dev/null ./...  # 컴파일 확인
go run .                     # 시연 실행: [1]~[4] 네 블록의 숫자를 비교해 읽는다
go test -v ./...             # 테스트: 불변식 위주라 머신 성능과 무관하게 통과해야 한다
go test -race ./...          # 동시성 주제라면 반드시: sink 전역 변수 접근에 race 가 없는지
go test -run=^$ -bench=. -benchmem -count=10 -benchtime=100ms > new.txt   # benchstat 입력
go test -run=^$ -bench=. -benchmem -count=10 -benchtime=100ms -cpu=1,4 > cpu.txt  # GOMAXPROCS 별
```

첫 명령에서 주목할 것은 `fmt.Printf` 의 지시자와 인자 타입이 맞는지다. `BenchmarkResult.NsPerOp()` 는 `int64` 이므로 `%10.1f` 가 아니라 `%d` 를 써야 하고, 이걸 틀리면 컴파일은 되지만 `go vet` 이 게이트에서 막는다. 두 번째 명령은 `-o /dev/null` 로 바이너리를 만들지 않고 컴파일만 확인한다. 세 번째 명령은 네 블록을 순서대로 찍는데, 각 블록의 "해석" 줄을 읽기 전에 숫자부터 먼저 보는 편이 좋다. 네 번째는 `Test` 함수들이 실제로 main.go 의 함수를 호출하는지 보여주고, 다섯 번째는 `sinkInt`, `sinkStr` 같은 전역 변수에 대한 접근이 단일 goroutine 안에 머무는지 확인한다.

benchstat 을 실제로 돌리려면 두 개의 파일이 필요하다. 변경 전 커밋에서 한 번, 변경 후 커밋에서 한 번 같은 명령을 돌려 `old.txt` 와 `new.txt` 를 만들고 `benchstat old.txt new.txt` 를 실행한다. `-count=10` 은 필수다. `-count` 없이 돌리면 표본이 1개라 benchstat 이 아무 판정도 하지 못한다. `-benchtime=100ms` 는 표본을 10개 모으면서도 전체 시간을 억제하기 위한 타협이다. 정밀도가 필요하면 `-benchtime=1s` 로 늘린다.

## 코드로 확인하기

`main.go` 는 네 개의 데모를 순서대로 부른다. `demoDeadCode` 는 1024 바이트 `[]byte` 를 `string` 으로 바꾸는 같은 작업을 두 방식으로 잰다. 결과를 `_` 로 버리는 쪽은 `allocs/op=0.0`, `ns/op` 는 한 자릿수 나노초가 나온다. 1024 바이트 변환이 실제로는 수백 나노초 걸리는 작업이므로, 이 숫자는 "빠른 코드"가 아니라 "지워진 코드"다. `sinkStr` 에 저장하는 쪽은 `allocs/op=1.0` 이고 `ns/op` 가 훨씬 크다. 두 숫자의 차이가 곧 컴파일러가 지운 일의 양이다.

`demoResetTimer` 는 `testing.Benchmark` 를 세 번 부른다. `benchSetupInside` 는 반복마다 1 KiB 를 새로 만들기 때문에 `allocs/op=1`, `B/op=1024` 가 찍힌다. `benchSetupOutside` 는 준비를 한 번만 하고 `b.ResetTimer()` 로 측정선을 그은 뒤라 `allocs/op=0`, `B/op=0` 이다. `benchStopTimer` 는 할당을 측정 구간 밖으로 뺐으므로 역시 `allocs/op=0` 이지만, 반복마다 `runtime.ReadMemStats` 를 부르는 비용 때문에 `ns/op` 가 오히려 커진다. 세 줄을 나란히 놓고 보면 "무엇을 재고 있는가"가 숫자만으로 드러난다. 각 줄 아래에 찍히는 "시도한 b.N" 궤적도 함께 보자. 준비 비용이 큰 벤치마크일수록 최종 N 이 작다.

`demoBenchGrowth` 는 같은 `benchWork` 를 두 번 돌리고 각 회차의 N 궤적과 최종 N, 총 소요 시간, ns/op 를 찍는다. 두 회차의 N 이 서로 다르고 ns/op 도 몇 퍼센트 어긋나는 것을 볼 수 있다. 이것이 "왜 단일 측정값으로 비교하면 안 되는가"에 대한 가장 직접적인 증거다. 궤적에 `-1` 이 찍히면 중간을 생략했다는 뜻이고, 궤적이 대략 100배씩 뛰는 것은 `run1` 이 목표 시간에서 N 을 역산하기 때문이다.

`demoStats` 는 `work(1000)` 을 두 번, `work(2000)` 을 한 번, 각각 5회씩 재서 `summarize` 로 요약한다. 같은 코드끼리 비교한 `A1 vs A2` 는 대개 `false`, 두 배 일한 `A1 vs B` 는 `true` 가 나온다. 여기서 `sd` 옆의 퍼센트가 상대 표준편차인데, 이 값이 5% 를 넘으면 사실상 그 벤치마크로는 5% 미만의 개선을 주장할 수 없다고 봐야 한다.

`main_test.go` 는 시간이 아니라 불변식을 검증한다. `TestRunNCallsExactlyN` 은 `runN` 이 정확히 n 번 부르는지, `TestBenchNInvariants` 는 N 궤적이 순증가하고 반환값이 궤적의 마지막과 같은지, `TestSummarize` 는 표본표준편차 공식이 맞는지, `TestSignificant` 는 잡음과 진짜 차이를 구분하는지, `TestSinkPreventsElimination` 은 sink 를 쓰면 최소 1 allocs/op 가 실제로 발생하는지, `TestTimerAccountingExcludesSetup` 은 준비를 측정 구간 밖으로 빼면 allocs/op 가 0 이 되는지 본다. 모두 결정적이라 CI 부하와 무관하다.

## 모르면 겪는 일

가장 흔한 증상은 `0 allocs/op` 를 "할당 없는 훌륭한 구현"으로 읽는 것이다. 실제로는 그 벤치마크가 아무 일도 하지 않았다는 뜻이다. 면밀히 보면 `ns/op` 가 0.3 처럼 CPU 클럭 주기보다 작은 값으로 나오는데, 이것이 결정적 신호다. 3 GHz CPU 에서 명령 하나에 약 0.33 ns 이므로, `ns/op` 가 0.3 근처라면 루프 오버헤드만 재고 있는 것이다. 이 상태로 리팩터링 전후를 비교하면 "300% 개선" 같은 허수 지표가 나오고, 그 벤치마크를 근거로 코드 리뷰를 통과시켰다가 실제 프로파일에서는 아무 변화가 없는 상황을 만난다.

두 번째 증상은 준비 비용이 측정 구간에 섞여서, 서로 다른 두 구현을 비교할 때 준비 코드의 차이를 구현 차이로 오독하는 것이다. 예를 들어 A 구현은 미리 버퍼를 만들고 B 구현은 매번 만든다면, 측정값 차이는 알고리즘 차이가 아니라 할당 횟수 차이다. 그런데 이걸 모르면 "B 알고리즘이 느리다"고 결론 내고 엉뚱한 곳을 최적화한다. 반대로 `b.ResetTimer()` 를 루프 안에 넣어버리는 실수도 있다. `ResetTimer` 는 호출마다 `ReadMemStats` 를 부르므로 매 반복 호출하면 측정 대상이 계측기에 묻힌다.

세 번째 증상은 `b.N` 을 루프 밖에서 쓰는 실수다. 예를 들어 반복마다 결과를 누적해서 마지막에 한 번만 sink 에 넣으면, 그 벤치마크는 N 이 커질수록 누적 비용이 커져서 ns/op 가 N 에 비례해 증가한다. benchstat 으로 보면 표준편차가 비정상적으로 크게 나오고, `-benchtime` 을 바꿀 때마다 결과가 달라진다. 또 `b.N` 을 나눗셈에 쓰거나 `b.N == 1` 인 첫 회차 결과를 출력에 포함시키면, 첫 회차는 워밍업이라 캐시가 비어 있어서 값이 튄다.

네 번째 증상은 `-count` 없이 benchstat 을 돌리는 것이다. 표본이 하나면 도구가 판정을 거부하거나, 운 좋게 나온 값을 그대로 보고하게 된다. 또 `-race` 를 켠 채로 성능 수치를 인용하는 실수도 흔하다. race detector 는 모든 메모리 접근에 그림자 상태를 붙이므로 5배에서 20배까지 느려진다. `-race` 는 정확성 검사용이고 성능 측정용이 아니다.

다섯 번째는 GC 와 캐시의 상호작용이다. `b.ReportAllocs` 로 할당을 재면, 할당이 많은 벤치마크는 측정 도중 GC 가 돌아서 ns/op 의 분산이 커진다. 이때 `GOGC=off` 로 재면 할당 비용만 깔끔하게 보이지만, 실제 서비스에서 GC 가 언제 도는지는 또 다른 문제다. 어느 쪽이든 한쪽만 보고 결론 내리면 틀린다. 실무에서 p99 가 GC 주기마다 튀는 문제는 마이크로 벤치마크로는 절대 재현되지 않는다.

## 언제 신경 쓰고 언제 무시하나

이 지식이 결정적인 것은 마이크로 벤치마크를 돌릴 때다. 대상 작업이 수 마이크로초 이하이고, 두 구현의 차이가 수 퍼센트 수준이며, 그 차이를 근거로 코드를 바꾸려 할 때는 sink, `ResetTimer`, `-count`, benchstat 네 가지가 모두 필요하다. 특히 라이브러리를 만든다면 사용자가 `go test -bench` 로 돌릴 벤치마크를 제공하게 되므로, sink 누락은 곧 잘못된 문서가 된다.

반대로 대부분의 애플리케이션 코드에서는 이 모든 것이 과잉이다. 요청 하나에 데이터베이스 왕복이 한 번 들어가면 그 비용은 수백 마이크로초에서 수 밀리초이고, 문자열 변환 최적화로 얻는 수백 나노초는 측정 자체가 불가능한 수준의 잡음이다. 이 규모에서는 벤치마크를 정교하게 만드는 시간보다 프로파일러(`pprof`)로 전체 핫패스부터 찾는 편이 압도적으로 효율적이다. 벤치마크는 이미 어디가 느린지 알고 있고, 그 느린 곳을 두 가지 방법으로 구현해봤고, 어느 쪽이 나은지 판단해야 할 때 쓴다.

경계선은 대략 "개선 폭이 그 벤치마크의 표본 표준편차보다 큰가"로 정하면 된다. 벤치마크를 3회 돌려서 상대 표준편차가 10% 라면 10% 미만 차이는 논하지 말고 다른 지표를 찾아야 한다. 표준편차 자체가 20% 를 넘으면 그 벤치마크는 설계가 잘못된 것이다. 준비 비용이 섞였거나, GC 가 끼어들거나, 타이머 해상도 아래에서 재고 있다는 뜻이므로 먼저 벤치마크를 고쳐야 한다. 수치를 더 모아서 해결되는 문제가 아니다.
