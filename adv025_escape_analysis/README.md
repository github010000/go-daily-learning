## 한 줄 요약

이스케이프 분석은 "이 값이 함수를 벗어나서 살아남을 수 있는가"를 컴파일 시점에 증명하는 정적 분석이다. 증명되면 스택에 두고, 증명하지 못하면 힙에 둔다. 스택 쪽은 회수 비용이 사실상 0 이고 힙 쪽은 GC 라는 청구서가 따라붙으므로, 이 판정 하나가 핫 패스의 성능을 갈라 놓는다.

`-gcflags=-m` 은 그 판정 결과를 사람이 읽을 수 있는 문장으로 찍어 주는 스위치다. `moved to heap: n`, `escapes to heap`, `does not escape`, `leaking param` 같은 메시지가 여기서 나온다. 메시지를 읽을 줄 알면 "왜 이 줄이 할당을 만드는가"를 추측이 아니라 확인으로 알 수 있다.

이 자료는 같은 로직을 스택 버전과 힙 버전으로 나란히 놓고, 호출당 힙 객체 수를 실제로 재서 차이를 숫자로 보여 준다. 그다음 같은 디렉토리에서 실제 컴파일러를 다시 불러 `-m` 출력을 화면에 띄운다. 분석은 컴파일 타임에만 일어나므로 실행 중에 흉내 낼 수 없고, 그래서 직접 컴파일러를 부르는 것이 유일하게 정직한 방법이다.

## 왜 이런 설계인가

스택 할당과 힙 할당의 비용 차이는 "조금 빠르다" 수준이 아니다. 스택 할당은 스택 포인터를 빼는 명령 한 줄이고, 회수는 함수가 return 할 때 프레임을 통째로 버리면 끝이다. 힙 할당은 mcache 에서 size class 를 골라 span 을 찾고, GC 회계 장부에 올리고, 포인터가 섞인 객체라면 write barrier 까지 지나야 한다. 여기에 할당률이 오르면 GC 가 더 자주 돌고, GC 는 살아 있는 객체를 훑기 위해 goroutine 을 세우고 스택을 스캔한다. 그래서 "가능하면 스택"은 미세 최적화가 아니라 처리량의 구조적 문제다.

그렇다고 프로그래머에게 선택권을 주지는 않았다. C 처럼 malloc/free 를 직접 시키면 use-after-free 와 double free 가 일상이 되고, Rust 처럼 lifetime 표기를 요구하면 타입 시스템과 씨름해야 한다. Go 는 GC 를 택했고, 그 순간 "언제 스택에 둘 수 있는가"는 프로그래머의 선언이 아니라 컴파일러가 증명할 수 있는 정리(Theorem) 문제가 되었다. 사용자는 아무 표기도 하지 않는다. 대신 분석이 실패하면 조용히 힙으로 간다. 그 침묵이 이 주제를 알아야 하는 유일한 이유다. 코드에는 아무 표시도 없는데 성능만 나빠지기 때문이다.

대안은 두 갈래였다. 하나는 Java HotSpot 처럼 일단 전부 힙에 두고 JIT 의 escape analysis 로 스칼라 대체(scalar replacement)를 하는 것이다. Go 는 JIT 가 없는 AOT 컴파일 언어라 실행 중에 판정을 바꿀 수 없다. 그래서 Go 의 판정은 바이너리에 영구히 박히고, 인터페이스 변환처럼 나중에 되돌릴 수 없는 경우에는 사용자가 코드를 고치는 수밖에 없다. 그 관찰 도구가 `-m` 이다. 다른 하나는 "항상 스택, 크면 힙" 같은 크기 기반 규칙인데, 크기만 봐서는 수명을 알 수 없으므로 안전하지 않다. 4KB 짜리 지역 배열이라도 주소가 밖으로 나가면 스택에 둘 수 없다.

분석이 보수적인 것도 설계다. 잘못 스택에 두면 해제된 메모리를 가리키는 포인터가 생기고, 그건 성능 문제가 아니라 메모리 안전성 사고다. 반대로 불필요하게 힙에 두면 느려질 뿐이다. 그래서 규칙은 "애매하면 힙"이다. `-m` 출력에 `does not escape` 가 보이지 않으면 기본값은 힙이라고 읽어야 한다. 분석이 실패했다고 경고를 띄우지 않는 것도 이 때문이다. 힙행은 정상 동작이고, 그냥 조금 비쌀 뿐이다.

마지막으로 인라이닝과의 관계가 중요하다. Go 컴파일러 파이프라인에서 인라이닝 패스는 escape 분석보다 앞에 있다. 그래서 같은 함수라도 인라인 되면 판정이 호출자 문맥에서 다시 내려지고, 반대로 인라인 예산을 넘겨 인라인되지 않으면 함수 단위 요약으로 판정된다. 데모 코드에 `//go:noinline` 을 붙인 이유가 여기 있다. 인라인 여부에 따라 측정값이 흔들리면 `-m` 메시지와 숫자가 서로 다른 이야기를 하게 된다.

## 어떻게 동작하는가

컴파일 파이프라인은 대략 noder/parser, types, inline, escape, walk, SSA 순으로 흐르고, 이스케이프 분석 본체는 `src/cmd/compile/internal/escape/escape.go` 에 있다. 분석은 함수마다 노드와 엣지로 이루어진 흐름 그래프(flow graph)를 만든다. 노드는 `&x`, `x` 자체, `new(T)`, 파라미터, 반환값, 필드 참조 같은 것이고, 엣지는 "이 값이 저기로 흘러간다"는 뜻이다. 예를 들어 `p := &x; return p` 는 `&x` 노드에서 반환 노드로 가는 엣지 하나로 표현된다.

각 노드는 `escapeUnknown`, `escapeNone`, `escapeHeap` 세 상태 중 하나를 갖는다. 시작은 unknown 이고, 흐름을 따라가며 힙이라는 근거를 만나면 heap 으로 확정된다. 그래프를 반복해서 전파하다가 상태가 더 이상 바뀌지 않으면 끝난다. 함수 경계를 넘을 때는 요약(summary)을 쓴다. `leaking param: x` 는 "이 파라미터가 밖으로 샌다", `leaking param content: x` 는 "파라미터가 가리키는 내용이 샌다", `param x leaks to ~r0` 은 "x 가 반환값 자리로 흘러간다"는 뜻이다. `-m` 에서 자주 보는 이 문장들이 바로 호출 그래프를 타고 전파되는 요약이다.

확정된 결과는 두 가지 문장으로 찍힌다. 지역 변수 자체가 힙으로 옮겨지면 `moved to heap: x`, 주소 표현식이 새어 나가면 `&x escapes to heap` 이다. 그다음 walk 단계에서 그 변수는 `runtime.newobject` 호출로 바뀌고, SSA 로 내려가면 결국 `runtime.mallocgc` 이 된다. 즉 `-m` 메시지는 최종 기계어에 남는 흔적의 이름표다.

인터페이스 변환은 `runtime.convT64`, `runtime.convTstring` 같은 conv 함수 호출로 내려간다. `convT64` 는 값이 256 미만이면 `runtime.staticuint64s` 라는 전역 배열의 원소를 가리키는 포인터를 그냥 돌려주고, 256 이상이면 `mallocgc(8, uint64Type, false)` 로 8 바이트 상자를 새로 뜬다(`src/runtime/iface.go`). 그래서 소스 한 줄이 런타임 값에 따라 할당 0 또는 1 이 된다. 이 데모의 `boxSmall` 과 `boxLarge` 가 본문이 완전히 같은데 결과가 다른 이유다.

슬라이스 확장은 `runtime.growslice` 가 담당한다. `append` 는 cap 이 모자랄 때만 이 함수를 부르고, growslice 는 새 backing array 를 잡아 원소를 복사한다. old cap 이 256 미만이면 두 배, 그 이상이면 약 1.25 배로 늘어난다. 원소 64 개짜리 int 슬라이스를 nil 에서 시작하면 cap 이 1, 2, 4, 8, 16, 32, 64 로 자라므로 할당이 7 번이다. 이 숫자가 데모 표에 그대로 나온다.

클로저는 `funcval{fn, 캡처한 값들}` 구조로 표현된다. 클로저 리터럴이 함수 밖으로 나가지 않으면 funcval 자체도 스택에 놓이고 캡처한 변수도 프레임에 남는다. 반면 클로저가 반환되거나 전역에 저장되면 캡처한 변수는 클로저보다 오래 살아야 하므로 `moved to heap: n` 이 찍히고 힙으로 옮겨진다. `-m` 을 두 번 주면(`-gcflags='-m -m'`) 어떤 엣지를 따라 그 결론에 도달했는지 이유까지 나온다.

## 돌려보기

이 디렉토리에서 그대로 실행할 수 있는 명령을 순서대로 적는다. 각 명령에서 무엇을 봐야 하는지도 함께 적었다.

```bash
go vet ./...                 # 정적 검사: noinline 함수에 쓰이지 않는 값이 없는지 확인
go build -o /dev/null ./...  # 컴파일 확인: 여기서 통과해야 아래 실험이 의미가 있다
go run .                     # 시연 실행: 할당 표 + 실제 -m 진단이 차례로 출력된다
go test -v ./...             # 테스트: 각 항목의 할당 횟수 불변식을 검증한다
go test -race ./...          # 동시성 주제라면 반드시: 전역 sink 를 쓰므로 확인 필요
```

여기에 이 주제에 필요한 명령을 더한다. 컴파일러 진단만 따로 보고 싶으면 다음을 쓴다.

```bash
go build -gcflags=-m -o /dev/null .        # 함수별 탈출 요약 한 줄씩
go build -gcflags='-m -m' -o /dev/null .   # 왜 그렇게 판정했는지 이유까지
```

`-m` 출력은 컴파일 대상 패키지 전체에 대해 나오므로 양이 많다. `grep` 으로 좁혀 보는 편이 빠르다.

```bash
go build -gcflags='-m -m' -o /dev/null . 2>&1 | grep -E 'moved to heap|escapes to heap' | head -40
go build -gcflags='-m -m' -o /dev/null . 2>&1 | grep -E 'closureEscapes|boxLarge|growNaive' | head -20
```

벤치마크로 할당량을 수치로 확인하려면 다음을 쓴다. `allocs/op` 열이 핵심이다.

```bash
go test -run '^$' -bench . -benchmem ./...
```

`go run .` 을 실행하면 먼저 9 행짜리 표가 나오고, 이어서 `go build -gcflags=-m` 을 직접 호출한 결과가 출력된다. `go` 명령이 PATH 에 없으면 안내 문구만 나오고 나머지는 정상 동작하므로, 그 경우 위의 명령을 손으로 실행하면 된다.

## 코드로 확인하기

표의 첫 열은 함수 이름, 둘째 열은 호출 1 회당 새로 생긴 힙 객체 수, 셋째 열은 그 이유다. `localPointerUse` 는 `0.00` 인데 `returnedPointer` 는 `1.00` 이다. 두 함수 모두 포인터를 만들지만 전자는 그 포인터가 함수를 벗어나지 않는다는 것이 증명되어 스택에 남고, 후자는 반환되므로 호출자가 언제까지 들고 있을지 알 수 없어 힙으로 간다. 여기서 배울 것은 "포인터 = 힙"이 아니라 "수명이 함수를 넘는가 = 힙"이라는 규칙이다.

`boxSmall(42)` 는 `0.00`, `boxLarge(1<<20)` 는 `1.00` 이다. 두 함수의 본문은 완전히 같다. 차이는 런타임에 넘어가는 값뿐이고, 256 미만이면 `runtime.staticuint64s` 재사용 경로를 타서 할당이 없고 그 이상이면 8 바이트 상자를 새로 뜬다. 이 숫자는 "인터페이스에 담으면 무조건 힙"이라는 통념이 절반만 맞다는 것을 보여 준다. 다만 256 미만 구간은 작은 정수 전용 예외이므로, 일반 규칙은 여전히 "인터페이스 변환은 대개 할당"이라고 잡는 편이 안전하다.

`growNaive(64)` 는 `7.00`, `growPrealloc(64)` 는 `1.00` 근처가 나온다. 64 개까지 자라는 동안 cap 이 1, 2, 4, 8, 16, 32, 64 로 일곱 번 바뀌기 때문이다. 여기에 복사 비용이 붙는다. 총 복사된 원소 수는 대략 1+2+4+...+32 = 63 개로, 최종 결과 64 개와 맞먹는다. 즉 cap 없이 append 하는 습관은 할당 7 배, 복사 2 배를 조용히 지불하는 것이다. `make([]T, 0, n)` 한 줄이 이걸 1 회로 줄인다.

`closureLocal` 은 `0.00`, `closureEscapes` 는 `1.00` 이상이다. 클로저 리터럴이 함수 안에서만 쓰이면 funcval 도 캡처한 변수도 스택에 있고, 반환되는 순간 둘 다 힙으로 간다. 실제로는 클로저 객체와 캡처 변수가 각각 할당되어 2 가 나올 수도 있는데, 그래서 테스트는 정확한 값이 아니라 "힙 버전이 스택 버전보다 많다"는 부등식으로 검증한다.

`main_test.go` 는 이 모든 것을 불변식으로 잡는다. 스택 버전의 할당이 0.5 미만인지, 힙 버전이 0.9 이상인지, 미리 잡은 슬라이스가 1.5 미만인지, naive 가 prealloc 보다 큰지를 확인한다. 정확한 값 대신 임계값과 부등식을 쓴 이유는 Go 버전이나 아키텍처에 따라 상수 몇 개가 달라질 수 있어서다. `TestCollectRowsIsConsistent` 는 표에 행이 조용히 빠지지 않았는지도 검사한다. 데모가 절반만 보이는데도 아무도 모르는 상황을 막기 위해서다.

## 모르면 겪는 일

가장 흔한 증상은 p99 지연이 GC 주기와 정확히 동기화되어 튀는데 CPU 프로파일에는 아무것도 안 보이는 것이다. 원인은 대개 핸들러 어딘가의 인터페이스 변환이다. `log.Printf("user %d", id)` 나 `fmt.Errorf("id %d: %w", id, err)` 는 가변 인자를 `[]any` 로 만들고 각 값을 힙 상자에 담는다. 요청당 몇 개 수준이라 벤치마크에서는 티가 안 나지만 초당 10 만 요청이면 초당 수십만 개의 상자가 생기고, 그 할당률이 GC 를 계속 깨운다. 힙 프로파일을 열면 `runtime.convT64` 가 상위에 있는데 정작 내 코드에는 인터페이스 변환이 한 줄도 안 보이는 상황이 된다.

파서나 로그 처리에서 문자열을 `[]byte` 로 바꾸는 습관도 같은 종류다. `for _, line := range lines { b = append(b, []byte(line)...) }` 는 줄마다 새 배열을 할당하고 복사한다. 문자열을 인덱스로만 읽으면 되는 일이면 변환 자체를 없앨 수 있고, 정말 바이트가 필요하면 재사용 버퍼에 `append(buf[:0], line...)` 으로 복사하면 할당이 0 이 된다.

슬라이스 확장은 더 조용하다. 요청마다 `var out []Item` 으로 시작해 append 로 채우면 항목 수에 따라 매번 여러 번 할당하고 복사한다. `sync.Pool` 로 슬라이스를 재사용해도 cap 이 작으면 결국 growslice 를 다시 부르므로, 풀에서 꺼낸 뒤 `if cap(s) < n` 검사를 넣어야 효과가 있다. 이걸 빠뜨리면 풀을 쓰는데도 할당 프로파일이 그대로인 결과를 만난다.

클로저 캡처는 의외의 자리에서 나타난다. `defer func() { metrics.Record(start, err) }()` 처럼 err 를 캡처하면 그 err 변수가 힙으로 옮겨지고, 그 변수에 담긴 값까지 줄줄이 영향을 받을 수 있다. 루프 안에서 goroutine 을 띄우며 루프 변수를 캡처하던 옛 패턴도 같은 문제를 만들었다. Go 1.22 에서 루프 변수 의미가 바뀌기 전에는 루프 변수 전체가 힙으로 가는 원인이었다.

## 언제 신경 쓰고 언제 무시하나

프로그램 시작 시 한 번 도는 코드는 무시해도 된다. 설정 파일 파싱, 플래그 처리, 초기 데이터 로딩에서 할당 몇 개를 아끼는 것은 전체 실행 시간에 측정 가능한 영향을 주지 않는다. `init()` 안에서 인터페이스를 몇 번 만들든 아무 일도 일어나지 않는다. 여기에 시간을 쓰는 것이 오히려 기회비용이다.

신경 써야 하는 조건은 명확하다. 요청당, 프레임당, 패킷당처럼 초당 수십만 번 이상 불리는 경로이면서, 그 안에서 객체를 만드는 경우다. 판단 기준은 절대량이 아니라 할당률(allocation rate)이다. GC 비용은 살아 있는 힙 크기와 할당 속도에 비례하므로, 큰 객체를 드물게 만드는 것보다 작은 객체를 미친 듯이 만드는 쪽이 더 아프다. `go test -bench . -benchmem` 의 `allocs/op` 가 0 이 아니어도 1~2 수준이면 대개 문제가 없다. 10 을 넘고 그 경로가 핫하면 그때 프로파일을 뜬다.

순서를 지키는 것도 중요하다. 측정 없이 `-m` 부터 들여다보면 의미 없는 곳을 고치게 된다. 먼저 `go test -benchmem` 이나 pprof 로 병목을 확인하고, 그 함수에서만 `-m` 을 읽고, 고친 뒤 같은 벤치마크로 회귀를 확인한다. `-m` 은 진단 도구이지 리팩터링 지침이 아니다. 분석 결과가 힙이라고 해서 항상 고쳐야 하는 것도 아니다. 코드 가독성을 해치면서 할당 1 회를 아끼는 거래는 대개 손해다.

- 진단 도구 개요: https://go.dev/doc/diagnostics

여기까지 읽고 데모를 한 번 돌려 보면, `-m` 출력의 한 줄이 곧 힙 프로파일의 한 줄과 대응한다는 감각이 잡힌다. 그 감각이 있으면 "왜 이 코드만 느리지"라는 질문에 추측 대신 실험으로 답할 수 있다. 다음 단계로는 `-gcflags='-m -m'` 을 켜고 인라이닝을 끄고 켜 가며 같은 함수의 판정이 어떻게 바뀌는지 관찰해 보는 것을 권한다. 인라이닝이 판정을 바꾸는 순간을 한 번 보면 이 주제의 절반은 이해한 것이다.
