## 한 줄 요약

성능 작업은 "고친다"가 아니라 **"가설을 세우고, 그 가설이 틀릴 수 있는 실험을 설계한다"** 는 절차입니다. 프로파일은 가설의 출처이고, 벤치마크는 그 가설을 반증하는 도구이며, 되돌리는 기준은 수정을 하기 전에 정해 둡니다.

## 왜 이런 설계인가

Go 팀이 pprof, trace, `testing.B` 를 표준 도구 안에 넣은 이유는 성능 문제의 대부분이 **직관과 어긋나기 때문**입니다. 사람은 "map 이 느릴 것 같다", "할당은 나쁘다", "락이 병목이다" 같은 그럴듯한 이야기를 쉽게 만들어 내지만, 실제 병목은 대개 눈에 안 띄던 `fmt.Sprintf` 나 `strings.Split` 의 숨은 할당, GC 가 돌리는 mark 작업, 혹은 아예 다른 서비스의 지연입니다. 그래서 도구가 먼저 있고, 도구가 가리키지 않는 곳은 고치지 않는다는 문화가 만들어졌습니다. `go.dev/doc/diagnostics` 가 profiling, tracing, debugging, runtime statistics 를 구분해서 설명하는 것도 "어떤 질문에는 어떤 도구"라는 대응을 가르치기 위해서입니다.

대안은 두 가지였습니다. 첫째는 **경험 많은 사람의 직관에 맡기는 것**입니다. 작은 팀에서는 통하지만, 하드웨어, 컴파일러 인라이닝, escape analysis, GC 의 버전별 변화가 직관의 유통기한을 짧게 만듭니다. 둘째는 **항상 켜진 상세 계측**입니다. 이것은 계측 자체가 측정 대상을 바꿉니다. pprof CPU 프로파일이 초당 약 100번의 샘플링(SIGPROF)으로 설계된 것은 오버헤드를 몇 퍼센트 이하로 묶어 프로덕션에서도 켤 수 있게 하려는 타협입니다. 그 대가로 샘플이 적은 짧은 함수는 보이지 않고, 통계적 신뢰는 실행 시간에 비례합니다.

벤치마크를 `testing` 패키지의 `b.N` 자동 조절 방식으로 만든 것도 같은 맥락입니다. 사람이 반복 횟수를 정하면 너무 짧아 타이머 해상도에 묻히거나, 너무 길어 아무도 안 돌립니다. 대신 "일정 시간이 찰 때까지 N 을 키운다"는 규칙으로 측정을 반복 가능하게 만들었습니다. 그러나 이 설계는 **한 번의 실행이 진실이라는 보증은 아닙니다.** CPU 주파수 변화, 다른 프로세스, GC 타이밍, 캐시 상태가 같은 코드의 결과를 흔듭니다. 그래서 `-count` 와 `benchstat` 으로 분포를 비교하는 것이 표준 절차가 되었습니다.

마지막으로 "되돌림"이 설계에 포함되어야 하는 이유가 있습니다. 최적화는 공짜가 아니고, 코드를 읽기 어렵게 만들고, 특정 입력 분포에 맞춰진 가정을 코드에 박습니다. 이득이 노이즈 안이라면 비용만 남습니다. 그래서 이 자료의 `Decide` 함수처럼 **수정 전에 판정 규칙을 정해 두는 것**이 중요합니다. 결과를 본 뒤에 기준을 정하면 사람은 항상 "그래도 좀 빨라졌네"라고 말하게 됩니다.

## 어떻게 동작하는가

루프는 다섯 단계입니다. (1) 재현 가능한 입력과 기준선(baseline)을 고정한다. (2) 프로파일에서 가설을 한 문장으로 쓴다. (3) 그 가설이 맞으면 반드시 변해야 하는 수치를 미리 적는다. (4) 한 가지만 바꾸고 같은 벤치마크로 재측정한다. (5) 미리 정한 규칙으로 유지 또는 되돌림을 결정한다. 가설이 반증되면 그것도 결과입니다. 여기서 "한 가지만 바꾼다"가 핵심이며, 두 개를 동시에 바꾸면 어느 쪽이 효과를 냈는지 알 수 없습니다.

가설의 재료는 프로파일입니다. CPU 프로파일은 `runtime/pprof` 가 SIGPROF 타이머로 스택을 샘플링해서 만들고, 힙(allocs) 프로파일은 `runtime.MemProfileRate`(기본 512KB 당 한 번)마다 할당 지점의 스택을 기록합니다(구현은 `src/runtime/mprof.go`). 샘플링이라는 점이 중요합니다. 작은 함수는 비율이 낮게 나오고, 인라이닝된 함수는 호출자에 합쳐져 보일 수 있습니다. 그래서 pprof 의 flat 은 "그 함수 자체", cum 은 "그 함수가 부른 것까지"라는 구분을 읽어야 하고, 가설은 "이 줄이 전체 CPU 의 N% 를 쓴다" 같은 **수치가 있는 문장**이어야 합니다.

이 디렉토리의 `main.go` 는 `genInput` 으로 결정적인 입력(small 4줄, large 2000줄)을 만들고, `testing.Benchmark` 로 ns/op, B/op, allocs/op 를 잽니다. 변형은 네 가지입니다. `baseline` 은 `strings.Split` 두 번과 `fmt.Sprintf` 를 쓰는 평범한 코드입니다. `presize` 는 "map 이 느릴 것"이라는 **추측**으로 `make(map, 1024)` 를 한 버전입니다. `fixed` 는 할당 프로파일이 가리키는 `Split` 과 `Sprintf` 만 `strings.Cut` 과 부분 문자열 키로 바꾼 버전입니다. `scratch` 는 "버퍼를 미리 잡으면 빠를 것"이라는 **과최적화**입니다. 모두 같은 결과를 내야 하므로 먼저 `sameResult` 로 정합성을 확인합니다.

판정은 `Decide` 가 합니다. 워크로드마다 ns/op, B/op, allocs/op 를 baseline 과 비교해서 허용치 `tol` 을 넘어 나빠진 지표가 하나라도 있으면 되돌리고, 어디서도 `tol` 이상 좋아지지 않아도 되돌립니다. `tol` 은 임의의 숫자가 아니라, 같은 baseline 을 두 번 재서 얻은 흔들림(spread)의 두 배와 10% 중 큰 값입니다. 노이즈 바닥을 모르면 "3% 빨라졌다"는 말은 의미가 없기 때문입니다. 또 `aggFixed` 에는 숨은 함정이 있습니다. `pair` 는 원본 줄의 부분 문자열이라 그대로 map 키로 쓰면 map 이 줄 전체의 메모리를 붙잡습니다. 그래서 처음 삽입할 때만 `strings.Clone` 을 합니다. 최적화가 새로운 메모리 보존 문제를 만들 수 있다는 예입니다.

## 돌려보기

```bash
go vet ./...                 # 정적 검사. 경고가 없어야 한다
go build -o /dev/null ./...  # 컴파일 확인
go run .                     # 시연 실행: [0]~[3] 네 구역을 순서대로 볼 것
go test -v ./...             # 테스트: 결정적 지표(allocs, bytes)만 단정하므로 항상 통과해야 한다
go test -race ./...          # 이 예제는 단일 goroutine 이지만 CI 습관대로 확인
```

`go run .` 에서는 [0] 구역의 네 줄이 모두 `true` 인지 먼저 보세요. [1] 에서 동일 코드를 두 번 잰 차이가 나옵니다. 이 숫자가 "이보다 작은 개선은 말할 수 없다"는 바닥입니다. [3] 에서 어떤 변형이 어떤 이유로 되돌려지는지 읽습니다.

프로파일에서 가설을 얻는 실제 절차는 다음과 같습니다.

```bash
# 1) 기준선을 여러 번 측정해서 파일로 저장 (분포를 얻기 위해 -count)
go test -run '^$' -bench 'BaselineLarge' -benchmem -count 10 > old.txt

# 2) 같은 벤치마크에서 CPU 와 메모리 프로파일 수집
go test -run '^$' -bench 'BaselineLarge' -benchmem -cpuprofile cpu.out -memprofile mem.out

# 3) 어디서 시간과 할당이 나오는지 본다. 가설은 여기서 나온다
go tool pprof -top cpu.out
go tool pprof -sample_index=alloc_space -top mem.out
go tool pprof -list 'aggBaseline' mem.out    # 줄 단위 할당량

# 4) 한 가지만 고친 뒤 같은 방식으로 저장하고 통계적으로 비교
go test -run '^$' -bench 'FixedLarge' -benchmem -count 10 > new.txt
# benchstat old.txt new.txt  (golang.org/x/perf/cmd/benchstat, 별도 설치 도구)

# 5) 워크로드를 바꿔 회귀가 없는지 확인
go test -run '^$' -bench 'Small' -benchmem -count 10
```

`-list` 출력에서 `fmt.Sprintf` 와 `strings.Split` 줄에 할당량이 몰려 있는지 보세요. `-run '^$'` 는 일반 테스트를 건너뛰어 벤치마크 시간에 섞이지 않게 합니다.

## 코드로 확인하기

`go run .` 의 [2] 구역에서 `baseline` 과 `fixed` 를 비교하면 large 워크로드에서 allocs/op 가 한두 자릿수 배로 줄고 ns/op 도 크게 내려갑니다. 줄 수가 2000, 줄당 쌍이 6개이므로 baseline 은 쌍마다 `Split` 슬라이스와 `Sprintf` 결과 문자열을 할당해 대략 수만 번의 할당이 나옵니다. fixed 는 distinct 키가 최대 35개이므로 키 복사와 map 성장 정도의 수십 번만 할당합니다. 이 비율이 "프로파일이 가리킨 곳을 고쳤다"는 가설이 확증된 증거입니다.

`presize` 는 흥미롭습니다. large 에서는 allocs 가 baseline 과 거의 같습니다. 병목은 map 이 아니었으므로 가설이 **반증**된 것입니다. 그런데 small 에서는 줄이 4개뿐인데 1024 칸 map 을 먼저 잡기 때문에 B/op 가 크게 늘어납니다. `scratch` 도 같습니다. 호출마다 64KB 를 잡으므로 small 의 B/op 가 `fixed` 의 수십 배가 됩니다. large 에서는 호출당 비용에 묻혀 거의 안 보이지만 small 에서는 지배적입니다. [3] 판정에서 `presize` 와 `scratch` 가 이유와 함께 REVERT 로 나오고 `fixed` 만 KEEP 으로 나오는 것이 이 자료의 핵심 장면입니다. ns/op 는 머신에 따라 달라지므로 숫자 자체보다 **부호와 비율**을 보세요.

`main_test.go` 는 시간에 의존하지 않고 결정적인 지표만 단정합니다. `TestVariantsAgree` 는 빈 줄, 잘못된 쌍(`x=y=z`), 빈 키를 포함한 경계 입력에서 모든 변형이 baseline 과 같은 결과를 내는지 봅니다. `TestGuessDoesNotHelpAllocs` 는 추측 수정이 allocs 를 10% 도 못 줄였음을, `TestProfileDrivenFixCutsAllocs` 는 프로파일 기반 수정이 5분의 1 이하로 줄였음을 `testing.AllocsPerRun` 으로 확인합니다. `TestOverOptimizationHurtsSmallInput` 은 `runtime.MemStats.TotalAlloc` 차이로 작은 입력의 회귀를 확인하고, `TestDecideRules` 는 합성 수치로 판정 규칙 자체를 검증합니다. 벤치마크 함수는 입력 생성 뒤에 `b.ResetTimer()` 를 호출해 준비 시간을 측정에서 뺍니다.

## 모르면 겪는 일

가장 흔한 증상은 **"벤치마크에서는 30% 빨라졌는데 프로덕션 p99 는 그대로"** 입니다. 마이크로벤치마크의 입력이 실제 요청 분포를 닮지 않았기 때문입니다. 이 자료의 large 에서만 재면 `scratch` 는 문제없어 보이지만, 실제 서비스가 작은 요청을 초당 수만 번 받는다면 요청마다 64KB 가 GC 의 할당 속도를 올려 mark 작업이 잦아지고, 그 대가가 CPU 프로파일에 `runtime.gcBgMarkWorker` 와 `mallocgc` 로 분산되어 나타납니다. 호출한 함수의 flat 시간에는 안 보이고 서비스 전체가 조금씩 느려집니다.

두 번째는 **dead code elimination 과 인라이닝**입니다. 결과를 전역 변수로 붙잡지 않으면 컴파일러가 호출을 지워 "0.3 ns/op" 같은 비현실적인 숫자가 나옵니다. 이 코드의 `sinkMap` 이 그 방어입니다. 반대로 벤치마크에서는 인라이닝되지만 실제 호출 경로에서는 안 되는 경우처럼 측정 환경과 실환경이 컴파일 결과 수준에서 달라질 수도 있습니다.

세 번째는 **노이즈를 효과로 착각**하는 것입니다. 노트북에서 한 번 돌려 "5% 개선"을 커밋하면, 다음날 다른 사람이 재현하지 못합니다. 열 쓰로틀링, 백그라운드 프로세스, 바뀐 GC 타이밍이 모두 같은 크기의 흔들림을 만듭니다. `-count 10` 과 `benchstat` 의 p-value 없이 한 자릿수 퍼센트를 말하면 안 됩니다.

네 번째는 **최적화의 부작용 누수**입니다. `aggFixed` 의 부분 문자열 키처럼, 할당을 줄이려고 원본 버퍼를 참조하면 메모리가 해제되지 않아 힙이 서서히 커집니다. 증상은 CPU 가 아니라 RSS 의 우상향이고 GC 가 더 자주 도는 것입니다. 또 sync.Pool 이나 캐시를 넣은 뒤 코너 케이스에서 오래된 데이터가 노출되는 정확성 버그도 같은 부류입니다.

**되돌려야 한다는 신호**는 다음과 같습니다. 개선폭이 측정 노이즈 안이다, 한 워크로드의 이득이 다른 워크로드의 손해로 상쇄된다, B/op 나 RSS 가 늘었다, 프로덕션 지표(p99, CPU 사용률)가 안 움직였다, 코드가 읽기 어려워진 만큼의 이득이 아니다, 그리고 가설의 예측("allocs 가 줄 것")과 실제 결과가 어긋났다. 마지막 신호가 가장 강합니다. 예측이 틀렸다면 원인을 이해하지 못한 채 우연히 얻은 수치이므로 다음 Go 버전에서 사라질 수 있습니다.

## 언제 신경 쓰고 언제 무시하나

이 절차가 중요해지는 때는 **측정 가능한 목표가 있을 때**입니다. SLO 위반, CPU 비용 청구서, 처리량 한계처럼 "이 숫자를 줄여야 한다"가 있고, 프로파일에서 상위 몇 개 함수가 전체의 상당 비율을 차지할 때입니다. 이때는 1% 를 벌기 위해 하루를 쓰는 것도 합리적일 수 있고, 위 루프를 엄격하게 돌릴 가치가 있습니다.

반대로 CPU 프로파일이 평평하고(상위 함수가 몇 퍼센트씩), 서비스가 지연 목표를 여유 있게 지키며, 요청 수가 작다면 최적화를 하지 않는 것이 정답입니다. 이 예제의 baseline 은 large 입력에서도 한 호출에 수 밀리초 단위입니다. 한 요청이 1000건 정도만 처리하는 서비스에서 `Sprintf` 를 지우는 일은 이득이 사실상 0입니다. 읽기 쉬운 코드가 이후 모든 수정의 비용을 낮춥니다.

작은 최적화를 반복하기 전에 **한 단계 위에서** 확인하는 것이 더 싸게 먹힙니다. 알고리즘과 I/O 횟수(DB 쿼리 수, 네트워크 왕복), 불필요한 직렬화가 먼저이고, 그 다음이 할당, 마지막이 인라이닝 같은 미세 조정입니다. 이미 있는 프로덕션 프로파일을 모은 뒤 PGO(profile-guided optimization)를 켜는 것도 코드를 안 바꾸고 얻는 이득이므로 수작업 최적화 전에 시도할 만합니다. 그리고 무엇을 하든 수정 전에 기준선과 판정 규칙을 적어 두는 습관만 지켜도 이 절차의 대부분의 가치를 얻습니다.
