## 한 줄 요약

`string` 과 `[]byte` 사이의 변환은 기본적으로 "새 배열을 잡고 바이트를 복사하는 일"이다. 언어 명세가 그렇게 못박아서가 아니라, `string` 의 불변성이라는 계약을 지키기 위해서다. 컴파일러는 escape analysis 로 결과가 함수 밖으로 도망가지 않는다는 것을 증명했을 때, 그리고 map 조회나 비교처럼 결과가 호출 순간에만 쓰이는 문맥을 알아봤을 때만 복사를 지운다. Go 1.20 에 추가된 `unsafe.String` 은 그 증명을 컴파일러 대신 프로그래머가 하겠다는 선언이고, 그 대신 계약 위반의 책임도 프로그래머가 진다.

## 왜 이런 설계인가

Go 의 `string` 은 불변이다. 이 한 문장 위에 여러 가지가 동시에 얹혀 있다. map 의 키 해시는 문자열이 만들어질 때 한 번 계산되어 버킷에 저장되는데, 키의 바이트가 나중에 바뀔 수 있다면 해시가 가리키는 위치와 실제 내용이 어긋나 "분명히 넣었는데 찾을 수 없는 키"가 생긴다. 문자열 상수는 실행 파일의 읽기 전용 세그먼트에 들어가고, 컴파일러는 상수 비교를 컴파일 시점에 접는다. 서로 다른 goroutine 이 같은 문자열을 읽을 때 락이 필요 없는 것도 불변성 덕분이다. 즉 불변성은 미학이 아니라 최적화의 토대다.

반대로 `[]byte` 는 가변이다. 두 타입을 같은 메모리 위에 겹쳐 놓으면 방금 열거한 성질이 전부 깨진다. 그래서 가장 단순하고 안전한 선택은 "경계를 넘을 때마다 복사"다. 대안은 세 가지 정도였다. 첫째, `string` 을 가변으로 만드는 것. 문자열을 빌더로 다루게 되고, 모든 사용처에 방어적 복사나 copy-on-write 가 필요해진다. 둘째, 모든 변환을 zero-copy 로 만드는 것. 별칭 문제를 언어 차원에서 허용해야 하고, 그러면 map 키 최적화와 상수 접기를 포기해야 한다. 셋째, Rust 처럼 lifetime 표기를 도입하는 것. Go 는 GC 를 택하면서 lifetime 표기를 언어에서 밀어냈고, 그 빈자리는 "정말 필요한 사람이 unsafe 로 직접" 남겨 두었다.

그래서 Go 의 전략은 "기본은 복사, 증명 가능한 곳만 생략"이다. 이 균형점은 컴파일러가 똑똑해질 때마다 조금씩 이동한다. map 조회용 변환이 복사 없이 처리되는 것도, 32바이트 이하 비탈출 변환이 스택 버퍼를 쓰는 것도 나중에 추가된 최적화다. 중요한 것은 이 최적화들이 언어 명세가 아니라 구현 세부라는 점이다. 명세는 `string(b)` 가 "b 의 바이트를 담은 문자열"이라고만 말하고, 그것이 복사인지 아닌지는 말하지 않는다.

비용 관점에서 보면 복사는 CPU 시간과 GC 압력을 동시에 만든다. 짧은 문자열 하나를 복사하는 것은 나노초 단위지만, 요청마다 수십 번씩 일어나면 힙에 쓰레기가 쌓이고 GC 주기가 짧아진다. 그래서 컴파일러는 "결과가 함수 밖으로 나가지 않는가"라는 아주 보수적인 조건을 만족할 때만 복사를 지운다. 증명에 실패하면 조용히 복사한다. 조용하다는 것이 이 주제의 핵심 위험이다. 코드는 똑같아 보이는데 프로파일의 모양만 달라진다.

## 어떻게 동작하는가

`string` 값은 런타임에서 두 워드짜리 헤더로 표현된다. 데이터를 가리키는 포인터와 길이다. `[]byte` 는 여기에 용량이 하나 더 붙은 세 워드짜리 슬라이스 헤더다. 두 타입의 차이는 사실상 "필드 하나"와 "불변성"뿐이고, 그래서 컴파일러는 조건만 맞으면 헤더를 재해석해서 복사를 건너뛸 수 있다. 실제 타입 정의는 `runtime/slice.go` 의 `slice` 구조체와 컴파일러 내부의 문자열 표현을 보면 확인할 수 있다.

`[]byte(s)` 는 `cmd/compile/internal/walk/convert.go` 에서 `stringtoslicebyte` 로 낮아지고, 런타임의 `runtime.stringtoslicebyte(buf *tmpBuf, s string)` 을 호출한다. 여기서 `buf` 가 핵심이다. 컴파일러가 "이 슬라이스는 함수 밖으로 나가지 않는다"고 판단하면 호출자의 스택 프레임에 있는 `tmpBuf` 의 포인터를 넘긴다. `tmpBuf` 는 `runtime/string.go` 에 `type tmpBuf [32]byte` 로 정의된 32바이트 배열이다. 길이가 32 이하이면 그 스택 버퍼를 슬라이스로 잘라 쓰고 힙 할당이 없다. 33바이트부터는 `rawbyteslice` 를 거쳐 `mallocgc` 로 힙을 잡는다. `buf` 가 `nil`, 즉 결과가 escape 하는 경우에는 길이와 무관하게 힙이다. 여기서 놓치기 쉬운 사실은 복사 자체는 두 경우 모두 일어난다는 것이다. 사라지는 것은 할당이지 복사가 아니다.

반대 방향은 `runtime.slicebytetostring(buf *tmpBuf, ptr *byte, n int)` 이다. 길이가 0 이면 전역 빈 문자열을 돌려주고, 1 이면 `runtime.staticuint64s` 라는 정적 테이블의 해당 바이트 자리를 가리키는 문자열을 만들어 할당을 피한다. 그 외에는 `buf` 가 있고 `n` 이 32 이하이면 스택 버퍼, 아니면 힙에 잡고 복사한다. 이 함수의 주석에 "buf 는 결과가 escape 하지 않을 때 nil 이 아니다"라고 적혀 있는 것이 이 메커니즘의 공식 설명이다.

컴파일러가 특별히 알아보는 문맥이 두 개 있다. `m[string(b)]` 처럼 map 인덱스 식의 키로만 쓰이는 경우와 `string(b) == x` 같은 비교의 피연산자로만 쓰이는 경우다. 이때는 `runtime.slicebytetostringtmp` 가 쓰인다. 이름 그대로 "임시" 문자열로, 바이트 배열을 가리키는 헤더만 만들어 넘기고 복사도 할당도 하지 않는다. map 조회 함수가 키를 조회 중에만 읽고 저장하지 않기 때문에 안전하고, 비교는 그 자리에서 끝나기 때문에 안전하다. 반대로 `m[string(b)] = 1` 처럼 키를 저장하는 식으로 쓰면 임시 문자열을 쓸 수 없어 정식 복사가 일어난다. 조회와 삽입이 같은 표기처럼 보이지만 비용은 다르다.

`s[a:b]` 는 복사하지 않는다. 헤더의 포인터를 `a` 만큼 밀고 길이를 줄일 뿐이다. 그래서 1MB짜리 문자열에서 10바이트를 잘라 보관하면 그 10바이트짜리 문자열 하나가 1MB 배열 전체를 살려 둔다. 복사를 피하는 최적화가 만들어 내는 반대 방향의 함정이다.

Go 1.20 에서 `unsafe.String(ptr *byte, len IntegerType) string` 과 `unsafe.SliceData`, `unsafe.StringData` 가 추가되면서 `reflect.StringHeader` 를 쓰던 관행이 공식 API 로 대체됐다. `unsafe.String` 의 조건은 문서에 명시돼 있다. `len` 은 음수일 수 없고, `ptr` 이 `nil` 인데 `len` 이 0 이 아니면 실행 시점 패닉이다. 그리고 가장 중요한 것: 반환된 문자열이 살아 있는 동안 `ptr` 이 가리키는 바이트를 수정하면 안 된다. 이 조건을 어기면 map 키가 깨지고, 같은 문자열을 다른 goroutine 이 읽고 있었다면 데이터 레이스가 된다. 또 `ptr` 이 가리키는 메모리는 문자열보다 오래 살아 있어야 한다. 스택 지역 배열을 감싸서 반환하면 escape analysis 가 놓치는 경우가 생긴다.

## 돌려보기

```bash
go vet ./...                 # 정적 검사 — unsafe 사용부가 걸리지 않는지 확인
go build -o /dev/null ./...  # 컴파일 확인 — go.mod 의 go 줄이 1.20 이상이어야 unsafe.String 이 컴파일된다
go run .                     # 시연 실행 — [1]부터 [7]까지 절별 수치를 본다
go test -v ./...             # 테스트 — 복사 의미론, 별칭, 할당 제거 조건 검증
go test -race ./...          # 동시성 주제라면 반드시 — 이 코드는 레이스가 없어야 정상이다
go run -gcflags=-m .         # escape analysis 결과 확인 — moved to heap / does not escape 를 본다
go test -bench . -benchmem ./...   # B/op 와 allocs/op 로 실제 비용 확인
go test -gcflags=all=-l ./...      # 인라인을 끄고 최적화가 얼마나 약해지는지 비교
```

`go run -gcflags=-m .` 에서는 `measureEscapingString` 쪽에 `moved to heap` 이 찍히고 `measureSliceLocal` 쪽에는 찍히지 않는 것을 보면 된다. `go test -bench . -benchmem` 에서는 escape 하는 벤치마크에 `1 allocs/op` 가, map 조회 벤치마크에 `0 allocs/op` 가 붙는지 확인한다.

## 코드로 확인하기

`[1]` 은 복사 의미론의 가장 기본이다. `[]byte(s)` 를 고쳐도 `s` 가 그대로이고, `string(b)` 이후에 `b` 를 고쳐도 문자열이 그대로다. 두 값이 서로 다른 배열을 가리킨다는 뜻이다. `[2]` 는 map 삽입이 왜 복사여야 하는지를 보여 준다. `m[string(key)] = 1` 로 넣은 키는 맵 안에 자기 바이트를 가진 상태로 들어가고, 그 뒤 `key` 를 바꿔도 `m["alpha"]` 는 여전히 1 이다. 반면 새로 계산한 `m[string(key)]` 는 0 이다.

`[3]` 이 이 글의 중심이다. 결과가 escape 하는 `string(b)` 는 `1.0` 이 나온다. 반면 비교에만 쓰는 변환은 `0.0`, map 조회 키로만 쓰는 변환도 `0.0` 이다. 같은 표기인데 할당 횟수가 다르다는 것이 요점이다. `[4]` 는 스택 버퍼의 크기 경계를 드러낸다. 길이 1, 8, 32 는 `0.0` 이고 33, 100 은 `1.0` 이다. 32라는 숫자가 런타임의 `tmpBuf` 크기다.

`[5]` 는 `unsafe.String` 판이 정말 같은 배열을 보는지(`true`)와, 계약을 어겼을 때 무슨 일이 벌어지는지를 보여 준다. 백킹 배열의 첫 바이트를 바꾸면 문자열 내용이 `"alpha"` 에서 `"olpha"` 로 바뀐다. 그런데 map 은 삽입 당시의 해시를 기억하고 있으므로 `len(m)` 은 1 인데 `m[s]` 는 발견되지 않는다. 맵이 조용히 깨지는 순간이다.

`[6]` 은 부분 문자열의 포인터를 찍는다. 두 포인터의 차이가 정확히 1000 이라는 것은 헤더만 잘랐다는 뜻이고, 10바이트짜리 문자열이 65536바이트 배열 전체를 붙잡고 있다는 뜻이기도 하다. `[7]` 은 unsafe 없이 복사를 피하는 표준 경로다. `strings.Builder.String()` 은 `0.0`, `io.WriteString` 은 `0.0` 인데 `w.Write([]byte(s))` 는 `1.0` 이다. `io.StringWriter` 인터페이스가 존재하는 이유가 여기에 있다.

`main_test.go` 는 이 중 시간에 의존하지 않는 성질만 골라 검증한다. 변환이 스냅숏인지, `byteView` 가 실제로 같은 배열을 보는지, escape 하는 변환보다 비교나 map 조회용 변환의 할당이 적은지, 32바이트 경계가 존재하는지, `Write` 와 `WriteString` 이 같은 바이트 수를 쓰는지를 본다. 모두 개수와 순서에 대한 불변식이라 부하가 걸려도 흔들리지 않는다.

## 모르면 겪는 일

가장 흔한 증상은 p99 지연이 GC 주기마다 튀는데 CPU 프로파일에는 잘 안 보이는 것이다. 핫 루프에서 `string(b)` 나 `[]byte(s)` 를 쓰면 시간은 `mallocgc` 와 `memmove` 로 흩어지고, 진짜 비용은 GC 가 힙을 훑는 쪽에서 발생한다. `-benchmem` 으로 `B/op` 를 보지 않으면 이 비용은 계속 숨어 있다.

`m[string(b)]` 로 조회하면 될 것을 `key := string(b)` 로 먼저 만들어 두고 조회하는 코드도 자주 보인다. 한 줄 차이인데 조회마다 힙 할당이 하나씩 생긴다. 반대로 map 삽입에 임시 문자열이 쓰일 것이라고 착각하는 경우도 있다. 삽입은 키를 보관해야 하므로 반드시 복사된다.

부분 문자열을 캐시하는 코드는 메모리 누수처럼 보인다. 응답에서 10바이트짜리 토큰만 잘라 슬라이스에 모아 두었는데 힙 프로파일을 보면 1MB짜리 버퍼가 수천 개 살아 있다. `s[a:b]` 가 복사가 아니라 별칭이라는 사실을 모르면 원인을 찾기 어렵다. 반대 방향으로, `bufio.Scanner` 의 `Bytes()` 가 돌려주는 슬라이스를 다음 `Scan` 이후에도 쓰면 내용이 조용히 바뀐다. 같은 백킹 배열을 재사용하기 때문이다.

`unsafe.String` 을 잘못 쓰는 경우는 더 조용하다. 백킹 배열을 재사용하는 버퍼 풀에서 문자열을 만들어 map 키로 넣고, 그 버퍼를 반납한 뒤 다시 채우면 맵의 키가 서로 다른 두 상태를 오간다. `len(m)` 은 맞는데 조회가 실패하고, 같은 키를 두 번 넣으면 하나로 합쳐진다. 여기에 동시 읽기까지 겹치면 데이터 레이스로 이어지고 `-race` 가 그제야 잡아낸다.

`[]byte("")` 가 `nil` 이 아니라는 것도 자주 발목을 잡는다. `if b == nil` 로 빈 값을 판정하는 코드는 `[]byte("")` 에 대해 거짓이 되어 다른 분기를 탄다. 길이로 판정해야 한다.

## 언제 신경 쓰고 언제 무시하나

초당 수십만 번 이상 변환이 일어나는 경로라면 반드시 본다. 특히 변환 대상이 32바이트를 넘어가면 스택 버퍼 특례가 사라지고 매번 힙을 잡는다. 반대로 요청 하나당 한두 번 일어나는 변환은 벤치마크에서 보이지도 않는다. 그런 곳에 `unsafe` 를 도입하는 것은 얻는 것보다 잃는 것이 크다.

`unsafe.String` 은 소유권이 한 함수 안에서 명확하고, 백킹 바이트가 절대 재사용되지 않으며, 문자열이 그 함수 경계를 넘지 않는다는 것을 스스로 증명할 수 있을 때만 쓴다. 라이브러리 경계를 넘겨 남에게 문자열을 돌려주는 자리에서는 쓰지 않는 것이 좋다. 그 순간 계약이 호출자에게 전염되기 때문이다.

최적화는 항상 측정 다음에 온다. `go test -bench . -benchmem` 으로 `allocs/op` 를 먼저 확인하고, `go run -gcflags=-m .` 으로 escape 여부를 확인한 뒤에 손을 대야 한다. 측정 없이 `unsafe` 를 넣으면 성능은 그대로인데 유지보수 비용만 늘어난다.
