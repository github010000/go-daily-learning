# Go 에러 처리 기초: error 는 값이다

## 한 줄 요약
Go에서 `error`는 특별한 타입이 아닌, `Error() string` 메서드를 가진 **인터페이스**일 뿐이며, nil과 비교하거나 `errors.Is`로 감싼 에러 체인을 탐색합니다.

## 왜 필요한가

에러 처리는 프로그래밍에서 가장 중요한 부분 중 하나입니다. 다른 언어(Java의 `try-catch`, Python의 `raise`)는 에러를 예외(Exception)로 처리하여 흐름을 강제로 끊는 방식을 쓰지만, Go는 **에러를 값**으로 다룹니다.

이렇게 설계한 이유는 무엇일까요? 첫째, **에러 처리가 코드의 가독성을 해치지 않습니다.** `if err != nil`은 길어 보일 수 있지만, 에러가 발생한 위치를 명확히 보여주며, 예외와 달리 호출 스택을 뒤져야 할 필요가 없습니다. 둘째, **에러가 '특수한 상황'이 아닙니다.** 에러도 하나의 값일 뿐이므로, 변수에 저장하고, 함수에 전달하고, 반환할 수 있습니다. 이는 에러를 더 유연하게 다룰 수 있게 합니다.

Python이나 JavaScript에서는 에러를 무시하기 쉽습니다(`try { ... } catch(e) {}` 안에서 `e`를 안 쓰는 경우). 하지만 Go에서는 **반환값을 `_` 에 버리든, `if err != nil` 체크를 건너뛰든, 컴파일러가 막아주지 않습니다.** 이것이 Go 에러 처리의 핵심이자 가장 위험한 부분입니다. "에러를 무시하지 않는다"는 것은 프로그래머의 **자율과 책임**을 의미합니다.

## 기본 사용

에러를 다루는 핵심은 세 가지입니다.

1. **nil 체크**: 가장 기본적입니다.
   ```go
   msg, err := greetingBad(name)
   if err != nil {
       // 에러 처리
       return err
   }
   ```
2. **sentinel error 비교 (`==`)**: `errors.New`로 정의한 전역 에러 변수는 동일 인스턴스이므로 `==`로 비교 가능합니다.
   ```go
   if err == ErrNameTooShort {
       // 특정 에러 처리
   }
   ```
3. **에러 체인 탐색 (`errors.Is`)**: `fmt.Errorf`의 `%w`로 에러를 감싸면, `errors.Is`로 원본 에러를 찾을 수 있습니다.
   ```go
   err = fmt.Errorf("컨텍스트: %w", originalErr)
   if errors.Is(err, ErrDBDown) {
       // 감싸진 ErrDBDown 발견
   }
   ```

## 돌려보기

이 디렉토리에서 그대로 실행할 수 있는 명령입니다.

```bash
go vet ./...      # 정적 검사 (사용하지 않는 import 등 확인)
go run .          # 시연 실행 (실수 버전 vs 고친 버전 출력 비교)
go test -v ./...  # 테스트 실행
```

`go vet`는 `"strings" imported and not used` 같은 import 오류를 잡아냅니다. `go run .`을 실행하면 **실수 버전**이 에러를 무시하고 계속 진행하는 모습과, **고친 버전**이 에러를 발견하면 즉시 중단하는 모습을 확인할 수 있습니다.

## 실전에서는 이렇게 쓴다

1.  **함수 반환값으로 에러 전달**: 모든 에러가 발생할 수 있는 함수는 `(result, error)` 쌍을 반환합니다. 에러를 로깅하거나 무시할지 결정하는 것은 **호출한 쪽**의 몫입니다.
    ```go
    func ReadConfig(path string) (Config, error) {
        data, err := os.ReadFile(path)
        if err != nil {
            return Config{}, fmt.Errorf("config 읽기 실패: %w", err)
        }
        // ...
    }
    ```
2.  **에러 감싸기(Wrapping)로 디버깅 정보 추가**: `%w` 동사를 사용해 에러에 컨텍스트를 추가하면, 에러가 발생한 경로를 쉽게 추적할 수 있습니다.
    ```go
    if userID == "user123" {
        // ErrDBDown에 "사용자 user123 처리 중 오류"라는 컨텍스트를 추가
        return fmt.Errorf("사용자 %s 처리 중 오류: %w", userID, ErrDBDown)
    }
    ```
    이렇게 감싸진 에러는 `errors.Is(err, ErrDBDown)`로 원래 에러를 찾을 수 있습니다.

## 흔한 실수

### 1. 에러를 무시한다 (`_` 사용)
에러를 `_` 에 버리는 것은 Go에서 가장 흔한 실수입니다. 에러가 발생했는데도 프로그램이 계속 실행되므로, 나중에 원인 파악이 어려운 상태로 빠질 수 있습니다.

**틀린 코드:**
```go
msg, _ := greetingBad(name) // 에러를 무시!
fmt.Println(msg) // 에러가 있어도 계속 실행
```

**어떤 일이 벌어지는지:** `greetingBad`이 `ErrNameEmpty`를 반환했는데, 호출자는 이를 무시하고 빈 문자열 `msg`를 사용합니다. 사용자에게 잘못된 메시지를 보여주거나, 빈 데이터로 작업을 계속할 수 있습니다.

**왜 그런지:** Go는 에러를 값으로 처리하므로, 컴파일러가 에러 무시 행위를 막아주지 않습니다. 프로그래머가 **"이 에러를 무시해도 안전한가?"**라고 스스로 물어봐야 합니다.

**고친 코드:**
```go
msg, err := greetingBad(name)
if err != nil {
    // 에러를 적절히 처리 (로깅, 반환, 기본값 설정 등)
    log.Printf("에러 발생: %v", err)
    return err
}
fmt.Println(msg)
```

### 2. 에러 체크를 늦게 한다
반환값을 먼저 사용하고, 그 뒤에 에러를 체크하는 패턴입니다.

**틀린 코드:**
```go
msg, err := greetingBad(name)
fmt.Println(msg) // 이미 msg를 사용!
if err != nil { // 에러 체크가 늦음
    return err
}
```

**어떤 일이 벌어지는지:** `name`이 비어있어 `msg`가 빈 문자열일 때, `fmt.Println(msg)`가 먼저 실행됩니다. 에러가 있더라도 이미 잘못된 데이터를 처리해버린 것입니다.

**왜 그런지:** 에러가 발생하면 **정상 로직을 실행해서는 안 됩니다.** 에러가 nil일 때만 정상 로직이 실행되도록 구조해야 합니다.

**고친 코드:**
```go
msg, err := greetingBad(name)
if err != nil {
    return err // 에러가 있으면 즉시 종료
}
fmt.Println(msg) // 에러가 없을 때만 실행
```

### 3. 에러 메시지에 대문자 시작과 마침표 사용
Go의 에러 메시지 관례를 위반하는 경우입니다.

**틀린 코드:**
```go
errors.New("이름이 비어 있습니다.") // 대문자 시작, 마침표 있음
errors.New("Error: 이름이 너무 짧습니다!") // 'Error:' 접두사
```

**어떤 일이 벌어지는지:** 코드는 컴파일되고 실행됩니다. 하지만 다른 Go 개발자가 읽을 때 혼란을 줄 수 있으며, 표준 라이브러리나 다른 패키지의 에러 메시지와 일관성이 없습니다.

**왜 그런지:** Go 커뮤니티의 강력한 관례(Convention)입니다. 에러 메시지는 **소문자로 시작**하고, **마침표(.)를 붙이지 않으며**, **'Error:', '에러 발생:' 같은 접두사를 붙이지 않습니다.** 에러 메시지는 "무엇이 잘못되었는지"를 간결하게 설명해야 합니다.

**고친 코드:**
```go
errors.New("이름이 비어 있습니다")
errors.New("이름이 너무 짧습니다")
```

### 4. `errors.New` 대신 `fmt.Errorf`를 무분별하게 사용
에러를 감쌀 필요가 없을 때도 `%w`를 사용하는 경우입니다.

**틀린 코드:**
```go
return fmt.Errorf("에러 발생: %w", ErrNameEmpty) // 불필요한 감싸기
```

**어떤 일이 벌어지는지:** `errors.Is(err, ErrNameEmpty)`는 작동하지만, 에러 체인이 불필요하게 길어집니다. 또한, `%w`는 `%v`보다 오버헤드가 약간 더 큽니다.

**왜 그런지:** `fmt.Errorf`의 `%w`는 **에러를 감싸기(Wrap)** 위해 사용됩니다. 단순히 에러 메시지를 포맷팅만 할 뿐, 에러 체인을 만들 필요가 없다면 `%v`를 사용하거나 `errors.New`를 사용하는 것이 더 명확합니다.

**고친 코드:**
```go
// 단순 에러 메시지 포맷팅
return fmt.Errorf("사용자 %s 처리 중 오류: %v", userID, ErrDBDown)

// 에러 감싸기 (에러 체인 생성)
return fmt.Errorf("사용자 %s 처리 중 오류: %w", userID, ErrDBDown)
```

## 주의할 점

-   **에러 무시의 유혹**: Go는 에러 무시를 컴파일 에러로 막지 않습니다. "에러를 무시해도 안전한가?"를 항상 self-check하세요. 안전하지 않다면 반드시 처리해야 합니다.
-   **`strings.Contains`로 에러 메시지 검증**: 테스트에서 에러 메시지 문자열에 특정 단어가 포함되는지 `strings.Contains`로 검증하는 것은 **취약**할 수 있습니다. 에러 메시지가 변경되면 테스트가 깨집니다. 가능한 한 `errors.Is`나 `==` 비교를 선호하세요.
-   **에러 체인의 깊이**: 너무 많은 에러 감싸기는 `errors.Is` 탐색 성능에 영향을 줄 수 있습니다. 불필요한 감싸기는 피하세요.
-   **`panic`과 `error` 혼동**: `panic`은 복구 불가능한 심각한 오류(메모리 부족, 프로그래밍 버그)에 사용해야 합니다. 일반 에러는 `error` 인터페이스를 반환해야 합니다. `panic`을 `recover`로 잡는 것은 특별한 경우(예: 서버 시작 실패)에만 사용하세요.

## 코드로 확인하기

`go run .` 을 실행하면 다음과 같은 출력이 나옵니다.

```
=== 에러 처리 기초 ===

--- 1. 에러 무시 vs 에러 처리 ---
[실수 1] "" -> 결과: ""
[실수 2] (후회) 에러 발생: 이름이 비어 있습니다
[고친 버전] "" -> 에러: 이름이 비어 있습니다
[실수 1] "김" -> 결과: ""
[실수 2] (후회) 에러 발생: 이름이 너무 짧습니다
[고친 버전] "김" -> 에러: 이름이 너무 짧습니다
[실수 1] "박고고" -> 결과: "안녕하세요, 박고고님!"
[고친 버전] "박고고" -> 성공: 안녕하세요, 박고고님!

=== 에러 비교하기 ===
...
```

**출력 해석:**
-   **실수 버전**은 `""` 입력에 대해 `msg`를 먼저 출력한 뒤, "후회" 메시지로 에러를 알립니다. 즉, **에러가 있어도 프로그램은 계속 진행**됩니다.
-   **고친 버전**은 `""` 입력에 대해 에러를 먼저 발견하고 즉시 `return`합니다. **정상 로직은 전혀 실행되지 않습니다.**
-   `"박고고"` 같은 정상 입력에서는 두 버전 모두 성공 메시지를 출력합니다.

`main_test.go`의 테스트는 `greetingBad`이 올바른 에러를 반환하는지, `wrapDBError`가 `errors.Is`로 탐색 가능한 에러 체인을 만드는지, sentinel error들이 올바르게 정의되었는지를 검증합니다.
