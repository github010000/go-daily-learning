## 한 줄 요약

Go 1.14의 비동기 선점(asynchronous preemption)은 함수 호출이 없는 tight loop가 GC의 stop-the-world를 수 초 이상 지연시키던 문제를 OS 시그널 기반으로 해결했다. 이제 대부분의 사용자 코드는 안전점(safe point)이 아닌 임의의 명령어 경계에서도 선점될 수 있다.

## 왜 이런 설계인가

Go의 가비지 컬렉터(GC)는 동시성 컬렉터이지만, 모든 goroutine을 잠시 멈춰야 하는 stop-the-world(STW) 단계가 여전히 존재한다. STW는 각 P(프로세서)가 자신의 실행 중인 goroutine을 안전점에서 멈추고, GC가 작업을 수행하는 동안 대기하는 구조다. Go 1.14 이전에는 선점이 협조적(cooperative)이었다. 즉, goroutine이 함수 호출이나 특정 검사 지점에 도달했을 때만 런타임이 제어권을 가져올 수 있었다. 그런데 함수 호출이 하나도 없는 `for { i++ }` 같은 tight loop는 안전점이 없기 때문에, 그 goroutine이 실행 중인 P는 STW 요청을 받아도 응답할 수 없었다. 이 때문에 GC 사이클이 수백 ms에서 수 초까지 늘어지거나, 심하면 무한히 지연되는 사고가 실제로 발생했다.

가장 먼저 떠올릴 수 있는 대안은 컴파일러가 모든 루프의 back edge마다 선점 검사 코드를 삽입하는 것이다. 그러나 이 방법은 모든 루프에 추가 코드가 생겨 바이너리 크기가 커지고, 루프가 짧은 경우에도 검사 오버헤드가 매번 발생한다. 또한 어떤 루프가 오래 실행될지 정적으로 예측하기 어렵기 때문에, 보수적으로 모든 루프에 넣는 것은 과도한 비용을 초래한다. 실제로 Go 팀은 이 방법을 오랫동안 검토했지만 성능 저하와 복잡성 때문에 채택하지 않았다.

결국 선택된 방법은 OS 시그널을 이용한 비동기 선점이다. 런타임의 sysmon goroutine이 오래 실행 중인 P를 발견하면 해당 OS 스레드에 SIGURG 시그널을 보낸다. 시그널을 받은 스레드는 실행 중인 사용자 코드를 임의의 명령어 경계에서 중단하고 런타임의 선점 핸들러로 진입한다. 이 방식은 컴파일러가 루프마다 검사 코드를 넣지 않아도 되고, 함수 호출 여부와 무관하게 동작한다는 장점이 있다. 대신 시그널이 도착하는 시점이 정확히 통제되지 않으므로, 런타임은 레지스터와 스택 맵을 정밀하게 보존해야 하고, write barrier처럼 도중에 선점되면 안 되는 구간에서는 지연시켜야 한다.

이러한 복잡성에도 불구하고 비동기 선점을 도입한 이유는, tight loop로 인한 STW 지연이 단순한 성능 저하가 아니라 서비스 중단급 장애를 일으킬 수 있었기 때문이다. 특히 GOMAXPROCS=1로 배포된 서비스에서 하나의 goroutine이 tight loop에 갇히면 다른 모든 요청이 실행되지 못한다. Go 1.14의 비동기 선점은 이 문제를 런타임 수준에서 근본적으로 해결한 것이다.

## 어떻게 동작하는가

비동기 선점의 시작은 runtime/proc.go의 sysmon이다. sysmon은 런타임이 시작할 때 생성되는 특수한 goroutine으로, 주기적으로(대략 10ms) 실행되어 여러 감시 작업을 수행한다. 그중 하나가 각 P의 실행 시간을 검사하여 너무 오래 실행 중인 goroutine에 선점 요청을 보내는 것이다. 선점 요청은 runtime/preempt.go의 preemptone 함수에서 처리되며, 해당 P의 상태를 조사한 뒤 실제로는 OS 스레드에 시그널을 보내는 방식으로 구현된다.

유닉스 계열에서 사용되는 시그널은 SIGURG이며, 이는 Go 런타임 전용으로 예약된 시그널이다. 시그널이 도착하면 커널이 현재 실행 중인 스레드를 잠시 멈추고, 런타임이 설치한 시그널 핸들러인 runtime/signal_unix.go의 sighandler로 제어가 넘어간다. 여기서부터 asyncPreempt2로 이어지며, 현재 goroutine의 PC, SP, 모든 범용 레지스터를 고루틴 스택에 저장한다. 이때 정확한 스택 맵과 포인터 정보는 컴파일러가 생성한 _FUNCDATA 메타데이터를 통해 얻는다.

모든 구간에서 선점이 가능한 것은 아니다. 예를 들어 GC의 write barrier가 활성화된 상태에서 goroutine이 선점되면 객체 그래프의 일관성이 깨질 수 있다. 또한 runtime.mallocgc나 lock을 소유한 구간에서 선점되면 교착 상태가 발생할 수 있다. 이러한 구간은 컴파일러가 unsafe point로 표시하고, 런타임은 asyncPreempt2에서 현재 PC가 안전한지 검사하여 안전하지 않으면 선점을 잠시 미룬다. 이 때문에 여전히 일부 구간에서는 비동기 선점이 지연될 수 있지만, 사용자 코드의 보통 tight loop는 안전점으로 간주되어 즉시 선점된다.

## 돌려보기

이 저장소의 디렉토리에서 다음 명령을 순서대로 실행하면, 비동기 선점이 켜진 경우와 꺼진 경우의 차이를 직접 눈으로 확인할 수 있다. 먼저 코드를 정적 검사하고 컴파일한 뒤, 기본 실행으로 측정한다.

```bash
go vet ./...                 # 정적 검사 — 불필요한 호출이나 경고가 없는지 확인
go build -o /dev/null ./...  # 컴파일 확인
go run .                     # 비동기 선점 켜진 상태로 실행
GODEBUG=asyncpreemptoff=1 go run .  # 협조적 선점만 사용하는 예전 방식 재현
go test -v ./...             # 합계 계산과 시간 불변식 검증
go test -race ./...          # -race에서도 데이터 경쟁 없이 통과
```

`go run .`을 실행하면 parent가 먼저 비동기 선점이 켜진 상태로 시연을 수행하고, 이어서 자기 자신을 child로 다시 띄워 `GODEBUG=asyncpreemptoff=1` 상태로 시연한다. 별도로 단독 실행도 가능하며, 이때는 위 명령에서 `GODEBUG=asyncpreemptoff=1 go run .`만 실행하면 협조적 선점만으로 동작한다.

첫 번째 실행에서는 main goroutine이 약 10~20ms 만에 다시 스케줄링되는 것이 출력된다. 두 번째 실행에서는 tight loop가 완전히 끝날 때까지 main goroutine이 멈춰 있으므로, 재개 시간이 수백 ms 이상으로 크게 늘어난다. 이 차이가 비동기 선점의 효과를 직접 보여준다.

## 코드로 확인하기

main.go의 `tightLoop` 함수는 의도적으로 함수 호출을 한 번도 사용하지 않는다. 컴파일러가 인라인하거나 최적화할 여지가 없는 순수한 산술 루프이며, 이것이 협조적 선점 방식에서 안전점이 없는 구간을 재현한다. main 함수는 `runtime.GOMAXPROCS(1)`을 호출해 하나의 P만 사용하게 만든다. 그래야 tight loop와 main goroutine이 같은 P를 공유하면서 선점 차이가 극명하게 드러난다.

`runTightLoopDemo`는 `go`로 tightLoop를 실행한 뒤 `runtime.Gosched()`를 호출해 현재 goroutine을 양보한다. 이 `Gosched`가 반환되는 시점이 곧 main goroutine이 다시 스케줄링된 시점이다. 비동기 선점이 켜져 있으면 약 10ms 안에 SIGURG가 tightLoop를 중단시키고 main을 재개하지만, 꺼져 있으면 tightLoop가 완전히 끝날 때까지 반환되지 않는다. 출력의 `main resumed after` 값이 핵심 지표다.

`main_test.go`는 `tightLoop`가 0부터 n-1까지의 합을 정확히 계산하는지 검증하고, `runTightLoopDemo`가 고루틴을 통해 그 합계를 반환하는지 확인한다. 시간에 의존하는 단정은 배제하고 합계와 시간 불변식만 검증하여 CI에서도 안정적이다. BenchmarkTightLoop는 루프 자체의 연산 속도를 측정한다.

## 모르면 겪는 일

첫 번째 증상은 GC pause 시간이 주기적으로 튀는 현상이다. 예를 들어 초당 수천 건을 처리하는 서비스에서 p99 지연 시간이 GC 주기마다 수백 ms로 치솟는데, CPU 프로파일에는 함수 호출이 없는 루프만 보이고 정작 GC STW 시간이 긴 것으로 나타난다. 이는 알고리즘 문제가 아니라 런타임 선점 문제이므로, 프로파일만 봐서는 원인을 찾기 어렵다.

두 번째 증상은 GOMAXPROCS=1로 실행되는 서비스에서 요청이 간헐적으로 멈추는 것이다. 하나의 요청 핸들러가 tight loop에 갇히면 다른 모든 요청이 실행되지 못한다. 예전 Go 버전에서는 이 문제가 수 초에서 수십 초까지 이어질 수 있었고, 실제 운영 환경에서 장애로 이어진 사례가 있었다. 비동기 선점이 도입된 이후에도 일부 unsafe 구간에서는 잠깐 멈출 수 있지만, 빈도와 지속 시간이 크게 줄었다.

세 번째 증상은 unsafe를 사용하는 코드가 1.14 업그레이드 후 갑자기 크래시하는 현상이다. 비동기 선점은 임의의 명령어 경계에서 레지스터 값을 보존하고 복원하기 때문에, 스택 포인터를 직접 조작하는 코드나 잘못된 unsafe 포인터 사용은 선점 핸들러와 충돌할 수 있다. 이는 보통 프로덕션 코드보다는 저수준 라이브러리에서 발생하며, 업그레이드 전에 unsafe 사용 부분을 점검해야 한다.

## 언제 신경 쓰고 언제 무시하나

비동기 선점은 Go 1.14 이후 기본 활성화되어 있으므로, 실제 개발자가 직접 설정할 일은 거의 없다. 대부분의 프로그램에서는 이 기능 덕분에 GC 지연이 개선되지만, 사용자가 체감하지 못할 정도로 작은 프로그램이라면 이 차이는 무시해도 된다. 오히려 GODEBUG로 끄는 것은 문제 재현이나 교육 목적 외에는 권장하지 않는다.

이 지식이 중요해지는 규모는 주로 p99 지연 시간을 수 밀리초 이내로 관리해야 하는 대규모 온라인 서비스다. 이러한 서비스에서는 GC STW 시간을 지표로 모니터링하고, 만약 tight loop에 의한 지연이 관찰되면 코드를 수정하거나 루프 안에 수동으로 `runtime.Gosched()`를 넣는 대신 런타임 버전을 확인해야 한다. 반면 배치 프로그램이나 CLI 도구에서는 오래 도는 루프가 있어도 사용자가 잠시 기다리면 그만이므로 크게 신경 쓸 필요가 없다.

또한 `GODEBUG=asyncpreemptoff=1`은 구버전 동작을 재현할 때만 사용해야 하며, 운영 환경에서는 절대 사용하면 안 된다. 이 플래그를 켜면 이전 버전에서 발생했던 GC 지연 문제가 그대로 재발하기 때문이다. 실제로는 1.14 미만 버전을 사용하는 경우에만 주의하면 된다.
