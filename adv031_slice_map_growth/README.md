## 한 줄 요약

`append` 는 "새 배열 할당 + 기존 원소 통째 복사"를 로그 스케일로 흩뿌려 삽입 한 번당 평균 O(1) 을 만들고, `map` 은 load factor 를 넘길 때마다 버킷 배열을 2배로 늘리되 이주 작업을 이후 삽입·삭제에 한 버킷씩 분산한다. 둘 다 "최대 1.25~2배까지 미리 잡아 두고, 그 대가로 복사 횟수를 로그로 줄인다"는 동일한 전략이며, 그래서 **크기를 아는 순간 `make` 에 넘기는 것**이 이 모든 비용을 0 으로 만드는 유일한 공짜 최적화다.

## 왜 이런 설계인가

Go 슬라이스는 길이를 바꿀 수 없는 값이다. `append` 가 실제로 하는 일은 새 backing array 를 `mallocgc` 로 잡고, 기존 원소를 `memmove` 로 복사하고, 슬라이스 헤더의 포인터·len·cap 을 갈아끼우는 것이다. 만약 매번 "정확히 필요한 만큼"만 잡는다면 n 번째 삽입마다 n-1 개를 복사하게 되고, n 개를 쌓는 총비용은 1+2+...+(n-1) = O(n²) 이 된다. 원소가 16바이트짜리 구조체이고 n 이 100만이면 이것만으로 수십 GB 의 memmove 가 발생한다. 그래서 여유분을 미리 잡는다. 여유분 비율을 r(다음 cap = r × 현재 cap)이라 하면, 한 번의 재할당에서 amortize 되는 복사량은 1/(r-1) 에 수렴하고, 낭비되는 메모리는 (r-1)/r 에 수렴한다. r 을 키우면 복사는 줄고 메모리는 늘어난다. 두 비용이 정면으로 충돌하는 파라미터이고, Go 는 이 하나의 숫자를 어디에 둘지 10년 넘게 조정해 왔다.

r = 2 는 복사가 삽입당 평균 1회, 즉 원소 하나를 넣을 때 평균적으로 원소 하나 만큼의 memmove 가 따라온다. 대신 n 이 2의 거듭제곱보다 조금만 커도 cap 이 두 배로 뛰어, 최악의 경우 필요한 양의 두 배 가까이 메모리를 붙잡는다. n=1..4096 구간에서 평균 (최종 cap / n) 을 재면 약 1.386 이다. r = 1.25 는 복사가 삽입당 평균 4회로 늘지만 평균 오버헤드가 약 1.12 로 떨어진다. Go 는 작은 슬라이스에서는 복사가 아프고 큰 슬라이스에서는 메모리가 아프다는 관찰 위에서, 작을 때는 2배, 커질수록 1.25배로 수렴하는 절충을 택했다.

Go 1.17 까지의 식은 이 절충을 두 조각으로 나눠 놓은 것이었다. cap 1024 미만이면 무조건 2배, 이상이면 1.25배. 문제는 그 경계에서 배율이 2.0 에서 1.25 로 계단처럼 떨어진다는 점이다. 원소 1023개를 담은 슬라이스와 1025개를 담은 슬라이스는 코드 한 줄 차이인데 메모리 오버헤드와 이후 재할당 빈도가 전혀 달라진다. 게다가 memmove 비용은 원소 크기에 비례하므로, 원소가 큰 구조체라면 이 계단이 실제 지연 스파이크로 관측된다. Go 1.18 은 이 계단을 없애고 `newcap += (newcap + 3*256) / 4` 하나의 연속 곡선으로 바꿨다. 작은 cap 에서는 2배에 가깝고, 큰 cap 에서는 1.25배로 매끄럽게 수렴한다. 상수항 768(=3×256)이 곡선을 잇는 역할을 하고, 그 결과 배율이 cap 의 함수로서 단조 감소한다. 오버헤드가 길이에 대해 연속 함수가 되었다는 것이 1.18 변경의 실질적 성과다.

map 은 다른 문제를 푼다. 해시 테이블에서 성능을 지배하는 것은 버킷당 평균 원소 수, 즉 load factor 다. Go 의 버킷은 8칸이고 load factor 는 6.5(`loadFactorNum=13, loadFactorDen=2`)다. 이 값을 넘으면 버킷 배열을 2배로 늘린다. 여기서 순진한 구현은 삽입 한 번이 트리거될 때 전체 원소를 새 배열로 재배치하는데, 원소 1000만 개짜리 map 이면 그 한 번의 삽입이 수 밀리초 동안 스레드를 붙잡는다. p99 지연에 민감한 서버에서는 이것이 곧 SLA 위반이다. Go 는 그래서 증분 이주를 택했다. 새 배열을 잡아 두고 `oldbuckets` 를 살려 둔 채, 이후의 삽입·삭제마다 버킷 하나씩 옮긴다. 그동안 조회는 두 배열을 모두 확인해야 하므로 약간 느려지지만, 어떤 단일 연산도 O(n) 이 되지 않는다. 대안은 처음부터 큰 배열을 잡거나, open addressing 으로 캐시를 노리는 것인데, 전자는 메모리를 낭비하고 후자는 삭제가 많은 워크로드에서 tombstone 이 쌓인다. 체이닝 + 증분 이주는 그 사이의 균형점이다.

슬라이스 쪽 대안도 검토할 만하다. 연결 리스트는 재할당이 아예 없고 삽입이 O(1) 이지만, 인덱스 접근이 O(n) 이고 노드마다 포인터 추적과 캐시 미스가 붙는다. 청크 리스트(rope)는 증분 확장이 가능하지만 `s[i]` 가 두 번의 역참조가 되고, `sort.Slice` 같은 연속 배열 전제의 API 와 맞지 않는다. Go 는 연속 배열 + 여유분을 택했고, 그 대가로 "재할당 시 통째 복사"라는 비용을 안고, 그 비용을 로그 스케일로 흩뿌려 amortize 했다. 언어 차원에서 이 선택을 한 이상, 프로그래머가 할 수 있는 일은 **크기를 미리 알려 주는 것** 하나뿐이다.

## 어떻게 동작하는가

슬라이스 성장은 `runtime/slice.go` 의 `growslice` 와 `nextslicecap` 에 있다. `nextslicecap(newLen, oldCap)` 이 새 cap 의 후보를 계산하고, `growslice` 가 `roundupsize(uintptr(newcap) * et.Size_)` 로 바이트 단위 올림을 한 뒤 다시 원소 수로 나눠 최종 cap 을 정한다. 여기서 두 층이 분리된다는 점이 중요하다. 첫째 층은 순수 산술이다. `newLen > 2*oldCap` 이면 그냥 `newLen`, `oldCap < 256` 이면 `2*oldCap`, 그 외에는 `newcap += (newcap + 768) >> 2` 를 `newcap >= newLen` 이 될 때까지 반복. 둘째 층은 `mallocgc` 의 size class 다. Go 의 할당자는 8, 16, 24, 32, 48, 64, 80, 96, ... 같은 고정 크기 클래스를 쓰고, 요청 바이트를 그중 하나로 올린다. 그래서 원소 8바이트짜리 `[]int` 에서 모델이 cap 5 를 요구하면 실제로는 40바이트 → 48바이트 클래스로 올라가 cap 6 이 되고, **그 6 이 다음 성장의 입력**이 된다. 2절에서 실제 시리즈가 모델 시리즈보다 항상 크거나 같은 이유가 이것이다.

복사 자체는 `memmove` 로 처리되지만, 원소 타입이 포인터를 포함하면(`et.PtrBytes != 0`) 단순 memmove 로 끝나지 않는다. 새 배열은 힙에 새로 잡힌 흰색 객체이고, 여기에 포인터를 그대로 복사하면 GC 의 삼색 불변식이 깨진다. 그래서 `growslice` 는 `bulkBarrierPreWrite` 로 write barrier 를 걸거나, 최근 버전에서는 `memmove` 후 `gcWriteBarrier` 경로를 태운다. 실무적 결론은 단순하다. 포인터를 담은 슬라이스는 여유 cap 만큼 GC 가 스캔해야 할 대상이 늘어난다. "일단 크게 잡아 두자"가 포인터 슬라이스에서는 GC 비용을 키우는 역효과가 될 수 있는 이유다. 또한 `append` 는 cap 이 남아 있으면 `growslice` 를 아예 호출하지 않는다. 컴파일러가 인라인한 비교 한 번으로 끝나므로, 재할당이 없는 append 는 사실상 `len` 증가와 원소 대입 두 줄이다. 비용은 전부 재할당 순간에 몰려 있다.

map 쪽 자료구조는 `runtime/map.go` 의 `hmap` 이다. 필드는 `count`, `flags`, `B`, `noverflow`, `hash0`, `buckets`, `oldbuckets`, `nevacuate`, `extra` 로 구성된다. `B` 는 버킷 수의 로그2 이고, 버킷 배열 크기는 `1 << B` 다. 각 버킷(`bmap`)은 8개의 슬롯을 가지며, 슬롯마다 해시 상위 바이트를 저장하는 `tophash` 배열이 앞에 붙는다. 조회는 `tophash` 를 먼저 훑어 대부분의 슬롯을 값 비교 없이 걸러 낸다. 삽입 시 `count+1 > 6.5 * 2^B` 가 되면 `hashGrow` 가 호출되고, 여기서 `oldbuckets` 에 기존 배열을 옮겨 두고 `B` 를 1 증가시킨 새 배열을 잡는다. 이후의 모든 `mapassign`/`mapdelete` 는 `evacuate` 를 통해 `nevacuate` 번째 버킷을 하나씩 새 배열로 옮긴다. `nevacuate` 가 `1 << (B-1)` 에 도달하면 `oldbuckets` 를 nil 로 만들고 이주가 끝난다. 이주 중에는 조회가 오래된 배열과 새 배열을 모두 봐야 하므로 일시적으로 느려진다.

`make(map[K]V, n)` 은 이 과정을 건너뛰게 해 준다. `makemap` 은 hint 로부터 필요한 `B` 를 역산해(`overLoadFactor` 루프) 버킷 배열을 처음부터 한 번에 잡는다. 여기서 실제로 줄어드는 것은 할당 횟수와 누적 바이트다. 재해시를 허용하면 B=0,1,2,... 마다 버킷 배열을 새로 잡으므로 누적 할당량이 최종 크기의 약 2배가 되고, 그 중간 배열들은 전부 GC 대상이 된다. hint 를 주면 그 2배가 1배가 된다. 참고로 Go 1.24 부터는 swiss table 기반 map 이 기본이 되어 버킷 구조와 이주 방식이 달라졌다. 위 관찰 코드는 `hmap.count` 를 `len(m)` 과 대조해 레이아웃이 맞는지 확인하고, 맞지 않으면 관찰을 포기하고 안내 문구를 출력하도록 만들어 두었다. load factor 와 "성장은 삽입에 분산된다"는 성질 자체는 그대로다.

## 돌려보기

```bash
go vet ./...                 # 정적 검사: unsafe 를 쓰는 map 관찰 코드가 걸리지 않는지 확인
go build -o /dev/null ./...  # 컴파일 확인
go run .                     # 4개 절의 관찰 결과 출력
go test -v ./...             # 테스트: 성장식, 불변식, 사전 할당 효과
go test -race ./...          # 동시성은 없지만 경쟁 검출기에서도 카운터 측정이 유지되는지 확인
go test -run XXX -bench . -benchmem ./...   # allocs/op 차이를 직접 확인
```

`go run .` 에서는 [1] 성장식 표의 `누적 복사` 와 `낭비%` 열, [2] 의 실제 cap 시리즈와 모델 시리즈의 차이, [3] 의 `할당 횟수` 열, [4] 의 `B` 가 증가하는 삽입 지점을 순서대로 보면 된다. `-benchmem` 을 붙이면 `BenchmarkAppendGrow` 와 `BenchmarkAppendPrealloc` 의 `allocs/op` 가 각각 10 대와 1 로 갈라지는 것을 볼 수 있다. map 관찰 부분은 Go 버전에 따라 `이주중` 이 항상 false 로 보일 수 있는데, swiss table 로 바뀐 런타임에서는 정상이다.

## 코드로 확인하기

[1] 은 순수 모델이다. n = 2^20 을 목표로 놓으면 "2배 고정"은 재할당 21회, 최종 cap 이 정확히 2^20 이라 낭비 0% 다. 반면 1.18 식은 재할당 30회 남짓, 최종 cap 이 요청보다 20% 이상 큰 값으로 끝난다. 이 숫자만 보면 "2배가 더 좋다"는 결론이 나오는데, 그건 n 을 2의 거듭제곱으로 골랐기 때문이다. 바로 아래 줄의 `n=1..4096 구간 평균` 이 그 착시를 깬다. 2배 전략의 평균 오버헤드는 약 1.39, 1.18 식은 약 1.12 다. 즉 2배 전략은 "운 좋은 n"에서만 0% 이고, 그 옆에서는 최대 100% 까지 낭비한다. 성장 계수를 평가할 때 단일 n 을 보면 안 되는 이유가 이 두 줄에 그대로 들어 있다. 이어지는 배율 곡선에서 1.17 식은 cap 512 에서 2.000, cap 1024 에서 1.250 으로 뚝 떨어지고, 1.18 식은 1.625 → 1.438 로 매끄럽게 내려간다.

[2] 는 실제 런타임이 뽑은 값이다. 여기서 봐야 할 것은 절대값이 아니라 "모델과 얼마나 다른가"다. `[]int` 는 원소가 8바이트이므로 size class 가 8, 16, 24, 32, 48, 64, ... 로 올라가고, 모델이 5 를 요구하는 지점에서 실제 cap 은 6 이 된다. 그 6 이 다음 성장의 입력이 되므로 실제 시리즈는 모델 시리즈보다 항상 앞서 달리고, 재할당 횟수는 모델보다 많아질 수 없다. 테스트 `TestActualSeriesNotSmallerThanModel` 이 검증하는 것이 정확히 이 부등식이다. 첫 cap 은 컴파일러가 스택에 얼마짜리 초기 버퍼를 잡는지에 따라 달라질 수 있어서 테스트는 `>= 1` 만 확인한다. 이런 값은 고정값으로 단정하면 안 되는 대표적인 예다.

[3] 은 사전 할당의 실제 이득이다. n = 8192 에서 `append` 를 재할당 허용으로 돌리면 13회 안팎, `make([]int, 0, n)` 으로 돌리면 1~2회 할당이 나온다. map 도 마찬가지로 hint 없이 8192 개를 넣으면 B 가 0 부터 11 까지 자라며 버킷 배열을 12번 안팎 잡고, hint 를 주면 2~3회로 끝난다. 누적 바이트는 약 2배 차이가 난다. 이 2배는 "최종 크기의 2배"라는 이론값과 일치한다. `ns/원소` 열은 머신 부하에 따라 흔들리므로 절대값을 믿지 말고 배수 관계만 보면 되고, 그래서 테스트는 시간이 아니라 `MemStats.Mallocs` 로만 판정한다.

[4] 는 map 의 성장 지점을 직접 찍는다. load factor 6.5 이므로 count 가 7, 14, 27, 53, 105, 209, ... 를 넘는 순간마다 `B` 가 1씩 증가한다. 즉 삽입 6번째까지는 버킷 하나(8칸)로 버티고, 7번째에서 두 번째 버킷이 생긴다. `이주중` 이 true 로 보이는 구간이 있으면 그 사이 모든 조회가 두 배열을 확인하고 있었다는 뜻이다. 이 열이 계속 false 라면 swiss table 기반 런타임이거나 레이아웃이 바뀐 것이고, 그때는 이 절을 참고용으로만 보면 된다.

## 모르면 겪는 일

가장 흔한 증상은 "CPU 프로파일 어디에도 없는데 p99 가 주기적으로 튄다"이다. 수십만 개를 `append` 로 쌓는 핫패스가 있으면 재할당 순간의 `memmove` 가 수백 마이크로초를 잡아먹는데, 이 시간은 `runtime.memmove` 로만 찍혀서 호출자 정보가 잘 드러나지 않는다. 프로파일을 아무리 뒤져도 내 함수가 안 보이고 런타임 함수만 보인다면 슬라이스 재할당을 의심해야 한다. 원소가 큰 구조체라면 한 번의 재할당이 수 밀리초가 되기도 한다.

`make([]T, n)` 과 `make([]T, 0, n)` 을 혼동하는 것은 컴파일도 되고 대부분의 테스트도 통과하는 실질적 버그다. 전자는 len 이 n 이므로 뒤에 `append` 하면 원소가 n 개 더 붙어 총 2n 개가 되고, 앞의 n 개는 제로값이 남는다. JSON 배열을 만들다가 앞에 null 이 n 개 붙는 식이다. 반대로 `make([]T, 0, n)` 에 인덱스로 값을 쓰면(`s[i] = x`) 패닉이다. cap 은 잡혀 있지만 len 이 0 이기 때문이다.

map 은 원소를 모두 지워도 메모리를 반납하지 않는다. 100만 개를 넣고 전부 `delete` 해도 버킷 배열과 `B` 는 그대로 남는다. "지웠는데 RSS 가 안 줄어요"의 대부분이 이것이고, 해결책은 주기적으로 새 map 을 만들어 복사하거나(`maps.Clone` 후 교체), 애초에 map 을 캐시로 쓰지 않는 것이다. 증분 이주 중인 map 은 조회가 두 배열을 보므로 일시적으로 느려지고, 삭제가 많아 overflow 버킷(`noverflow`)이 쌓이면 조회가 체인을 따라가며 느려진다. 해시가 나쁜 키 타입(예: 포인터 상위 비트만 다른 값)을 쓰면 몇 개 버킷에 몰려 최악의 경우 선형 탐색이 된다.

포인터를 담은 슬라이스에 습관적으로 큰 cap 을 주는 것도 함정이다. 여유 칸은 GC 가 훑어야 할 범위를 그대로 늘리고, `growslice` 는 포인터 원소에 대해 write barrier 를 걸어야 한다. 메모리를 아끼려고 2배로 잡았는데 GC 마킹 시간이 늘어 p99 가 나빠지는, 원인과 결과가 반대 방향인 상황이 만들어진다.

## 언제 신경 쓰고 언제 무시하나

원소 수가 수백 개 수준이고 그 슬라이스를 만드는 코드가 요청당 한 번도 안 불린다면 아무것도 하지 마라. `make([]T, 0)` 으로 쓰든 cap 을 주든 사용자 체감도, 프로파일도 구분하지 못한다. map 도 마찬가지로, 프로그램 수명 동안 수십 개 키만 다루는 설정 map 이라면 hint 는 순수한 노이즈이고 코드만 길어진다.

신경 써야 하는 조건은 명확하다. 첫째, 원소 수가 수만 이상이고 그 생성이 요청 핫패스에 있는 경우. 둘째, 원소가 큰 구조체(수십 바이트 이상)여서 재할당 한 번의 memmove 가 밀리초급인 경우. 셋째, 같은 슬라이스를 초당 수천 번 새로 만드는 경우. 넷째, p99 에 민감한 서버. 이 네 조건 중 하나도 안 걸리면 `make` 의 세 번째 인자는 잊어도 된다.

판단은 감이 아니라 `go test -bench . -benchmem` 으로 한다. `allocs/op` 가 1~2 로 안 떨어지면 아직 재할당이 남아 있다는 뜻이고, 그때만 cap 을 손보면 된다. 반대로 hint 를 과대 추정해도 큰 문제는 없다. 메모리만 조금 더 쓰고, 어차피 성장은 일어나지 않는다. 과소 추정은 그냥 원래대로 성장할 뿐이므로, 크기를 모르면 대충이라도 큰 쪽 수를 주는 편이 낫다. 단, 위에서 봤듯이 포인터 슬라이스에서의 과대 추정은 GC 비용으로 되돌아온다는 점만 기억하자.
