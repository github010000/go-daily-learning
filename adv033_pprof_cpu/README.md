## 한 줄 요약

Go 의 CPU 프로파일은 "실행 시간을 정확히 잰 값"이 아니라 100Hz 로 날아오는 SIGPROF 신호가 그 순간 CPU 위에 있던 스택 하나를 주워 담은 표본 통계이고, 그 표본은 벽시계가 아니라 프로세스가 태운 CPU 시간을 세므로 syscall 대기와 sleep 은 아예 보이지 않으며, 같은 파일을 flat 과 cum 이라는 두 관점으로 집계한다는 사실을 모르면 최적화 대상을 정반대로 고르게 된다.

## 왜 이런 설계인가

모든 함수에 계측 코드를 심는 방식(instrumentation)은 정확하다. 대신 대가가 크다. 함수 진입과 이탈마다 카운터를 갱신해야 하고, 그 갱신 자체가 측정 대상의 실행 시간을 바꾼다. 짧은 함수일수록 왜곡이 심해져서 "측정을 켜면 프로그램이 느려지고, 느려진 프로그램을 측정한다"는 자기 참조 문제가 생긴다. Go 는 컴파일러에 계측을 넣지 않고, 런타임이 비동기 신호로 스택을 훔쳐보는 쪽을 택했다. 대신 정확도를 포기했다.

두 번째 이유는 상시 켜 둘 수 있어야 한다는 것이다. 트레이싱 계열 도구는 모든 이벤트를 기록하므로 초당 수백 MB 를 만들 수 있고, 그래서 짧은 구간에만 켠다. 반면 표본 방식은 CPU 시간 10ms 당 스택 하나만 남기므로 30초 실행에 3000 개, 압축하면 수십 KB 다. 상시 켜 두거나, 문제가 생겼을 때 프로세스에 붙어서 뜨거나, 심지어 운영 서버에서 초 단위로 떠도 견딘다. 이 자유를 얻으려고 "정확한 시간"을 버린 것이다.

세 번째는 표본의 편향을 설계에 명시했다는 점이다. SIGPROF 는 `setitimer(ITIMER_PROF)` 로 걸리는데, 이 타이머는 벽시계가 아니라 프로세스가 소비한 CPU 시간을 기준으로 만료된다. 그래서 CPU 프로파일의 표본 수는 실행 시간이 아니라 CPU 초에 비례한다. 이건 결함이 아니라 정의다. "내 프로그램이 CPU 를 어디에 썼는가"라는 질문에는 이 정의가 정확히 맞고, "내 요청이 왜 3초 걸렸는가"라는 질문에는 완전히 틀린 도구다. 두 질문을 구분하라고 타이머 종류를 CPU 시간 기준으로 고른 것이다.

네 번째는 flat 과 cum 을 저장 시점이 아니라 조회 시점에 나눈다는 점이다. pprof 파일에는 표본마다 스택 전체가 들어 있고, "이 함수 몸통에서 몇 번 인터럽트됐나(flat)"와 "이 함수를 거치는 스택에서 몇 번 인터럽트됐나(cum)"는 파일을 읽는 쪽에서 계산한다. 덕분에 `-cum` 정렬, `-focus`, `-ignore`, `-peek` 같은 필터를 원본 손실 없이 적용할 수 있다. 대신 집계 규칙을 모르면 같은 파일에서 정반대 결론을 뽑게 된다.

## 어떻게 동작하는가

`runtime/pprof.StartCPUProfile(w)` 를 부르면 내부적으로 `runtime.setcpuprofile(rate, ...)` 가 호출되고, 유닉스 계열에서는 `runtime/signal_unix.go` 의 `setProcessCPUProfiler` 를 거쳐 `setitimer(ITIMER_PROF, {10ms, 10ms})` 가 설정된다. 이 시점부터 커널은 프로세스가 CPU 시간 10ms 를 소비할 때마다 SIGPROF 를 하나씩 배달한다. 신호는 프로세스 단위이고 커널이 임의의 스레드를 골라 준다.

신호를 받은 스레드는 런타임의 `sigprof` 핸들러로 들어간다. 여기서 하는 일은 현재 실행 중인 goroutine(`m.curg`)을 고르고, 그 스택을 위로 훑어 반환 주소들을 모은 뒤, 나노초 타임스탬프와 함께 `profBuf` 에 밀어 넣는 것이다. 이 버퍼가 가득 차면 표본을 버리고 손실 카운터를 올린다. 즉 100Hz 는 상한이고, 신호 처리 중이거나 스택을 복사하는 도중에 도착한 신호는 잃을 수 있다.

`pprof.StopCPUProfile()` 은 타이머를 끄고, 남은 `profBuf` 를 비우면서 `runtime/pprof/protobuf.go` 의 `profileBuilder` 로 protobuf 를 조립한다. 최종 파일은 gzip 으로 압축된 `Profile` 메시지다. 구조는 단순하다. `string_table`(필드 6)에 모든 문자열을 모아 두고, `function`(필드 5)은 이름을 문자열 인덱스로만 가리키며, `location`(필드 4)은 주소와 `line`(함수 id + 줄 번호) 목록을 갖고, `sample`(필드 2)은 `location_id` 배열과 `value` 배열을 갖는다. `sample_type` 은 보통 [samples/count, cpu/nanoseconds] 두 개이고 `period` 는 10000000ns 다.

중요한 세부 두 가지가 있다. 첫째, `location` 하나에 인라인된 여러 프레임이 담길 수 있다. 그래서 location 을 함수 하나로 매핑하면 인라인된 함수가 통째로 사라진다. 둘째, `sample.location_id` 의 첫 원소가 leaf 이고 마지막이 root 다. flat 은 첫 원소에만 더하고, cum 은 스택 전체를 훑으며 더하되 재귀 호출은 중복해서 세지 않는다. 이 두 규칙이 이 글의 코드에서 `decodeCPUProfile` 이 하는 전부다.

마지막으로 syscall 구간이 왜 비는지 보자. 블로킹 `read(2)` 안에 있는 M 은 Go 스택을 CPU 위에 올려놓지 않는다. 커널 안에서 잠들어 있으므로 user CPU 시간이 늘지 않는다. SIGPROF 는 프로세스가 CPU 를 쓴 만큼만 오므로 신호 자체가 오지 않고, 신호가 와도 찍을 Go 스택이 없다. 그래서 벽시계 250ms 를 기다린 구간의 프로파일 표본은 0 에 가깝고, 같은 250ms 를 곱셈으로 태운 구간의 표본은 약 25 개가 된다. 이 차이가 곧 "CPU 프로파일은 지연 분석 도구가 아니다"라는 말의 실체다.

## 코드로 확인하기

1번 구간은 `burnCPU(300ms)` 를 프로파일로 감싼다. 출력의 "표본 N개, 벽시계 기준 기대값 M개" 에서 N 과 M 이 거의 같게 나오는 이유는, 이 구간이 goroutine 하나로 CPU 를 계속 물고 있으므로 프로세스 CPU 시간이 곧 벽시계 시간이기 때문이다. "표본/CPU초" 값이 100 근처로 찍히면 SIGPROF 주기가 실제로 10ms 라는 뜻이다. 이 값이 100 보다 훨씬 작으면 표본 손실이 있다는 것이고, 훨씬 크면 다른 프로세스와 코어를 나눠 쓰면서 CPU 시간이 더 들어간 것이다.

표로 찍히는 부분에서 봐야 할 것은 `hotTop`, `hotMiddle`, `hotLeaf` 세 줄이다. 세 줄의 cum 이 모두 같은 값인데 flat 은 `hotLeaf` 에만 몰려 있다. cum 은 "이 함수를 지나는 스택에서 잡힌 표본"이므로 스택이 항상 같은 세 함수에게는 같은 값이 붙는다. flat 은 "이 함수 몸통에서 잡힌 표본"이므로 실제 곱셈-덧셈이 있는 `hotLeaf` 에만 붙는다. `hotTop` 의 flat 이 0 이 아니고 한두 개 찍힌다면 그건 호출과 반환 사이의 몇 명령이다.

2번 구간은 20만 번 호출해도 표본이 0 이라는 것을 보여준다. `callTinyMany` 는 수백 마이크로초만 쓰므로 표본 주기 10ms 를 한 번도 채우지 못한다. 여기서 나오는 `tiny flat=0 cum=0` 은 "이 함수가 빠르다"는 뜻이 아니라 "이 실행 시간 규모에서는 이 도구로 볼 수 없다"는 뜻이다. 이 구분이 실무에서 가장 자주 무너진다.

3번 구간은 파이프 `read(2)` 로 250ms 를 기다린다. 표본이 0~1 이고 user CPU 시간이 0.00x 초로 찍힌다. 벽시계는 250ms 인데 표본은 없다. 이 한 줄이 "CPU 프로파일로 지연 문제를 못 잡는 이유"의 전부다.

4번 구간은 1번 구간의 요약을 다시 읽어 세 함수의 flat/cum 을 나란히 찍는다. 5번 구간은 goroutine 4개로 같은 시간만큼 태워서, 벽시계가 그대로인데 표본이 몇 배로 늘어나는 것을 보여준다. 표본이 CPU 초를 센다는 주장의 직접 증거다.

`main_test.go` 는 두 갈래를 검증한다. `TestSyntheticProfileFlatAndCum` 은 손으로 만든 3-표본 프로파일로 디코더와 집계 규칙을 결정적으로 확인하고(flat 3/0, cum 3/3), `TestProfileInvariants` 는 실제로 뜬 프로파일에서 flat <= cum <= total 과 "CPU 를 태운 함수가 표본의 절반 이상"이라는 불변식만 본다. `TestBlockedSyscallInvisible` 은 블로킹 구간 표본 수가 CPU 구간 표본 수보다 작다는 비교만 하고, 절대 시간은 단정하지 않는다.

## 모르면 겪는 일

가장 흔한 증상은 "CPU 프로파일이 텅 비어 있는데 서비스는 느리다" 이다. 외부 API 호출, DB 대기, 파일 IO, `time.Sleep`, 채널 대기가 지배적인 서비스에서 30초 프로파일을 떠 보면 표본이 수십 개뿐이고 상위에는 런타임 함수만 몇 개 보인다. 이걸 "프로파일러가 고장났다"거나 "CPU 는 안 쓰는데 왜 느리지"로 해석하면 원인을 영원히 못 찾는다. 이때 필요한 것은 wall-clock 프로파일, `go tool trace`, 또는 block/mutex 프로파일이다.

두 번째는 flat 과 cum 을 뒤집어 읽는 경우다. `go tool pprof -top` 은 기본이 flat 정렬인데, 누군가 cum 표를 보고 1등에 오른 HTTP 핸들러나 `main` 함수를 "가장 느린 함수"로 지목해 리팩터링한다. 효과는 0 이다. 그 함수의 flat 은 0 에 가깝고, 시간은 전부 그 아래 어딘가에서 쓰이고 있다. 반대로 "cum 이 큰 함수를 최적화하면 되나" 싶어서 라우터를 손봐도 역시 0 이다.

세 번째는 표본 수가 적을 때의 노이즈다. 표본이 100 개 미만이면 상위 함수 순위가 실행할 때마다 바뀐다. 20 표본짜리 프로파일을 보고 3등과 5등을 비교하며 최적화 우선순위를 정하는 것은 동전 던지기와 크게 다르지 않다. 증상은 "프로파일을 다시 뜨면 상위가 계속 바뀐다"로 나타난다.

네 번째는 인라인과 런타임 잡음이다. 작은 함수는 컴파일러가 인라인해서 별도 프레임이 사라지고, 그 비용은 부모의 flat 에 합쳐진다. 그래서 "내가 만든 그 함수가 프로파일에 안 나온다"는 상황이 정상적으로 발생한다. 또 `runtime.mallocgc`, `runtime.gcBgMarkWorker`, `runtime.scanobject` 가 상위에 뜨는 것을 애플리케이션 코드 문제로 오해하기 쉽다. GC 는 실제로 CPU 를 쓰므로 그건 진짜 비용이지만, 해법은 그 함수를 고치는 것이 아니라 할당을 줄이는 것이다.

다섯 번째는 syscall 시간을 CPU 시간으로 착각하는 것이다. 어떤 서비스는 CPU 프로파일이 조용한데 `top` 에서는 CPU 사용률이 100% 로 보인다. 이건 대개 커널이 시간을 쓰는 구간(복사, 페이지 폴트, TLS 처리)이거나 다른 프로세스다. user CPU 와 system CPU 를 구분하지 않으면 이 차이를 못 본다. 코드의 `cpuSeconds` 가 user CPU 만 읽는 것도 이 구분 때문이다.

## 언제 신경 쓰고 언제 무시하나

표본이 100 개 미만이면 이 도구의 순위는 신뢰하지 말 것. 100Hz 이므로 CPU 초 1 초가 표본 100 개다. 즉 30초 실행해도 CPU 를 1초만 썼다면 표본은 100 개 남짓이고, 그걸로 상위 10개를 비교하는 것은 의미가 없다. 프로파일을 뜨기 전에 "이 실행이 CPU 를 몇 초 쓸까"를 먼저 계산하고, 1초 미만이면 벤치마크를 쓰는 편이 정확하다.

지연 문제에는 CPU 프로파일을 꺼내지 말 것. p99 가 GC 주기마다 튀는 문제, 특정 요청만 3초 걸리는 문제, 커넥션 풀 고갈 문제에는 이 도구가 구조적으로 답을 줄 수 없다. SIGPROF 는 CPU 를 쓴 프로세스에만 오고, 대기 중인 goroutine 은 스택에 안 잡힌다. 이런 질문에는 `go tool trace`, block 프로파일, 또는 외부 APM 이 맞는 도구다.

반대로 CPU 를 오래 쓰는 배치, 인코딩/디코딩, 압축, JSON 직렬화, 암호 연산처럼 "순수하게 CPU 를 태우는 뜨거운 경로"를 찾을 때는 100Hz 표본이 놀랍도록 정확하다. 이런 작업은 한 함수가 수백 ms 를 연속으로 쓰므로 10ms 주기로 수십 번 잡히고, 노이즈가 자연히 평균된다. 이럴 때 flat 상위 3개를 보는 것이 가장 빠른 지름길이다.

작은 프로그램이나 일회성 스크립트에서는 잊어도 된다. 수십 ms 짜리 실행에는 표본이 몇 개 안 되고, 그 시간에 `testing.B` 로 벤치마크를 돌리는 편이 훨씬 정밀하다. 이 글이 중요해지는 규모는 대략 "한 번 실행에 CPU 를 몇 초 이상 쓰고, 어디가 뜨거운지 모르는" 순간부터다.
